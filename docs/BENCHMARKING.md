# Benchmarking

Moved from CLAUDE.md (#202): the `mipfeas` benchmark, the harness's pre-flight checks and baselines, configs, tuning subsets, filtering and the oracle, and the release archive. The rules here bind exactly as they did there.

## Benchmarking

`bench/` has scripts for MIPLIB benchmarks — `run_benchmark.py` runs instances, `analyze_results.py` parses results.

**The benchmark is `mipfeas`, and `PLATO` is not a name for it.** `mipfeas` is 233 instances selected from the MIPLIB 2017 benchmark collection with the known-infeasible ones excluded, scored by the primal integral — Bussieck and Dirkse (GAMS), [*Expanding the Focus: Introducing the mipfeas Benchmark*](https://www.gams.com/blog/2026/03/expanding-the-focus-introducing-the-mipfeas-benchmark/), 17 March 2026, a collaboration including Mittelmann, ZIB and NVIDIA. That post is the citation for the instance set and the metric. **`PLATO` is the hostname of Hans Mittelmann's benchmark server at Arizona State** ([plato.asu.edu](https://plato.asu.edu/bench.html)) — where results are *posted*. It is not an acronym and expands to nothing; university machines are often just named after philosophers. So write `PLATO` only where the results host is genuinely meant, and `mipfeas` for the benchmark, its instance list, its 233, its metric and its protocol. The identifiers follow: the environment variables are `MIPFEAS_*`, the chunked launcher is `bench/run_mipfeas.sh`, the instance list is `bench/instances_mipfeas.txt` and the results tree is `bench/results/mipfeas/`. Two classes of file may carry a `plato` spelling **deliberately**, and neither is a miss to fix: the archived trees under `dist/`, whose manifests record those names, and every **generated output**, which is frozen at the bytes its generator wrote — the instance lists (`instances_tuning.txt`, `instances_confirm*.txt`, `instances_heldout48.txt`, `bench/ablation_effort/*.txt`) and the captured tables (`bench/headline/tables.txt`, `bench/ablation_search/tables*.txt`). **Not one byte of a generated output, comment lines included** — an edit to a *label* is as damaging as an edit to a recorded path. Two reasons. Its header records the invocation that produced it, and rewriting that records a run that never happened. And `make_tuning_set.py`'s `file_digest` hashes a candidate pool's **whole file, comments and all**, so `instances_tuning.txt` pins `bench/ablation_effort/informative.txt` by sha256 — re-wording informative.txt's first line silently breaks that pin, which is the one signal the field exists to raise. Change the generator's string when the wording should move; the file catches up the next time it is genuinely re-derived.

**Where MIPLIB lives.** The collection is **not** at a fixed path: `bench/download_miplib.sh` and `run_benchmark.py --data-dir` share a search path — explicit argument, then `$MIPLIB_DIR`, then `~/data/miplib`, then `/tmp/miplib` — and the first directory holding more than 200 `.mps.gz` files wins. It is 3.5 GB, so it lives once per machine outside every checkout; `/tmp` is probed (an existing copy is reused) but never written to, since it does not survive a reboot. **That search path and its >200 threshold are defined twice, once in bash and once in Python**, and drift between them is silent and expensive — the downloader writes one directory while the benchmark reads another. Three tests in `bench/test_run_benchmark.py` parse the shell script and assert both against the Python constants; keep them passing rather than editing one side alone.

**Don't pass `--threads`** (or set `threads=` in an `.opts` file) unless asked — let HiGHS use its default; forcing `threads=1` collapses each heuristic to a single worker (the right setting for reproducibility, the wrong one for a throughput benchmark).

**The vanilla baseline is always a separately built unpatched binary** (`--vanilla-binary`, matching tag). Two binaries is the design, not a preference or a fallback, and `run_benchmark.py` enforces it:
- `vanilla` is not a `CONFIG_SELECTIONS` entry — it names a binary, not a selection, and carries no options. `build_plan` raises when the config is asked for without `--vanilla-binary`.
- `check_vanilla_binary` runs the named binary **with no arguments** before the first solve, refusing it if the banner carries `mip-heuristics patch active` or reports a version other than the `GIT_TAG` in `cmake/FetchHiGHS.cmake`. **The no-argument invocation is the whole trick**: `--version` never reaches `highsLogHeader`, so it prints neither the marker nor the `Running HiGHS <v> (git hash: <h>)` form, and a probe there would silently pass a patched binary. Only the *version* decides anything in that banner; the git hash is captured for a manifest and compared by nothing, which is why `BANNER_RE` accepts `[^)]+` there — HiGHS sets `GITHASH` to the literal `n/a` when configured outside a git repository, so a distro package would otherwise be refused for "printing no HiGHS banner" in a message quoting that banner.
- The probe is **symmetric**: `--binary` must carry the marker and match the tag, because a stock HiGHS there has none of the options the configs set and every run would exit 255. Each binary is probed only if a plan uses it, so `--configs vanilla` alone never touches the patched build.
- `check_known_options` is the second half of the pre-flight and runs against **every distinct binary the run will use**: HiGHS exits 255 without solving on an unknown option name, and `--extra-options` applies to every config, so one bad key fails every instance of every config on that binary and leaves a resume loop relaunching a campaign that cannot advance. It asks the binary one key at a time (HiGHS stops reading an options file at the first unknown key, so one probing run names one offender) rather than filtering on a `mip_heuristic_` prefix: of the eighteen `mip_heuristic_*` names a patched build carries, **seven are upstream's own** and legal on both binaries — `mip_heuristic_effort` plus the six `mip_heuristic_run_*` switches (`feasibility_jump`, `rens`, `rins`, `root_reduced_cost`, `shifting`, `zi_round`) — so a prefix rule would refuse a valid sweep and a hardcoded list of the other eleven would need editing on every option change.
- `run_mipfeas.sh` has **no default for the vanilla binary at all** — no fallback to `$BINARY`, no `command -v highs` PATH search: a baseline whose binary was discovered rather than named is a baseline nobody chose. The empty `--vanilla-binary` it may pass is read as "not given", the same convention `--data-dir` uses.
- `bench/check_vanilla_equivalence.py` compares the configuration where **both sides disable FeasibilityJump** (every effort zeroed plus `mip_heuristic_run_feasibility_jump=false`, against upstream's own switch), which is the part worth proving: that injecting the heuristics moves neither presolve, nor B&B, nor the LP path. It spells the patched side's options as `config_options("off")` rather than writing them out, so a sixth heuristic cannot be added and quietly left running in the one configuration that proves the patch is inert.

**Killed runs are kept, not discarded.** HiGHS checks its clock between work units, so one long simplex solve at the root can pass `time_limit` without returning to look. `run_benchmark.py` keeps the partial stdout and appends a `TIMEOUT: process killed after Ns` marker, which `parse_highs_log.py` turns into `killed` and a `Killed (timeout)` status, and `analyze_results.py` lists under "Killed runs". Those logs still score correctly — T1st and the primal integral read the incumbent lines, never the Solving report the run never reached — and are deliberately *not* retried on resume, since rerunning reproduces the same hang. Only a kill before the binary printed anything becomes a `.log.err`, which is the shape that does get retried.

Patched binaries self-identify with a `mip-heuristics patch active` line right after the version banner (injected by `apply_patch.cmake`) — the version/githash banner alone is identical between patched and unpatched builds of the same tag (at equal clone depth; see the `GIT_SHALLOW` note in `docs/DEVELOPMENT.md`).

`run_benchmark.py` leaves `log_dev_level=3` off behind `--dev-log`: level 3 and the headline timing are not the same run.

### Configs

`run_benchmark.py`'s config surface is exactly one entry of `CONFIG_SELECTIONS` per selectable subset of the five heuristics, with no aliases, plus the one name that is *not* a selection: `vanilla`. `KNOWN_CONFIGS` is the union, and `resolve_config` raises against it.

Subset names **join with `+`** (`fj+fpr`): a comma is legal in a directory name but not free in a generated table or in LaTeX. Subset names list heuristics in selection order — the presolve chain in dispatch order, then `fpr_lp` — so one subset has exactly one spelling (`fpr+fj` is not a config, and neither is `fpr_lp+fj`). The thirty-one subsets are **generated** from the ordered name tuple `SUITE_ORDER` rather than written out, so the chain-order spelling holds by construction. The full five-element subset is spelled `all`, its long-standing alias, so it appears once.

**A config name *excludes* by zeroing.** `config_options` returns `mip_heuristic_<name>_effort = 0` for every heuristic the name does not list and sets nothing for the ones it does, so a named heuristic runs at the binary's shipped default. Two consequences follow and are deliberate: `all` sets **nothing at all**, so it is exactly "the binary's defaults"; and naming `scylla` or `fpr_lp` does **not enable** them, because both ship at zero — a config that means to run either needs `--extra-options` beside it. A config option wins over an `--extra-options` pin of the same key, which is what keeps a tree named for one configuration from holding runs of another; the collision warning is suppressed when the two values agree numerically, because a finalist sweep spells its own zeros and would otherwise print a line per zeroed heuristic per launch.

**`config_options` raises on an unknown config name**, rather than returning `{}` and producing a fully populated, plausible-looking, completely meaningless results tree. A config name carries **no budget of its own**: every heuristic runs at its shipped default, and moving one for a run goes through `--extra-options`. `build_plan` is the single place a name's two consequences — which binary, which options — are chosen together; choosing them at separate use sites is how a name picks one branch's binary and the other branch's options. A run that solved but ignored its configuration is routed to `<inst>.log.err` like a non-solving exit. There is exactly one such shape — a positive `mip_heuristic_fj_effort` with `mip_heuristic_run_feasibility_jump=false` and nothing else enabled, which `run_presolve` warns about and `CONFIG_IGNORED_WARNINGS` greps for. A *mistyped* selection cannot produce one: HiGHS name-checks and range-checks an effort option, so it is an exit-255 refusal at `check_known_options` time.

### Tuning subsets

`bench/make_tuning_set.py <vanilla-results-tree> --instances bench/instances_mipfeas.txt --size N --seed S` derives a stratified tuning list and prints the stratum table to stderr (the list goes to `--output`, stdout by default).

It stratifies on **vanilla time-to-first-feasible** — read through `parse_highs_log`, not a second parser — because that is the axis the mipfeas primal integral responds to. `bench/instances_small.txt` is stratified on *optimality* solve time and stays exactly as it is, being the recorded input of earlier budget work and the set per-heuristic budget work runs on.

Strata are half-open intervals split at `--boundaries` (default `1,10,100,600`) plus a `never` bucket and a `>=600s` overflow bucket — **a solution found at or past the time limit is hard, not never-feasible**, and must not be filed as one. Allocation is largest-remainder proportional in *integer* arithmetic, with `--min-per-stratum` seats reserved off the top so a 3-of-233 stratum is not rounded out of the set it was stratified for. **The integer arithmetic is load-bearing**: where the integer remainders are a mathematical tie, float shares carry fractional noise that sorts them into a different order and hands the seat to the wrong stratum — an observed test failure, not a hypothetical. No cap is applied on top: `alloc <= population` follows from `rest <= room_total`, and a sweep in `bench/test_make_tuning_set.py` checks it rather than the code clamping something that cannot bind.

The emitted header records source tree, config, seeds, boundaries, allocation rule and both distributions, and deliberately carries **no timestamp**: same tree plus same `--seed` must be byte-identical. It refuses (exit 2) any tree not covering the reference list for every seed of the config, and two log shapes that would otherwise be binned as never-feasible: a *truncated* log (no solving report), and one reporting a finite primal bound with no incumbent line — which is what a source code missing from `parse_highs_log._INCUMBENT_SOURCES` looks like, i.e. what a HiGHS bump produces. `parse_highs_log` already `warnings.warn`s on that second condition; `unusable_reason` mirrors it so the diagnosis becomes a refusal instead of a mis-binned instance in the smallest stratum. `--allow-incomplete-seeds` is the one documented escape, and it is recorded in the header.

### Instance filtering, the config oracle, and reference data

`--instances FILE` restricts any report to an instance list and `--exclude-instances FILE` removes one, applied in that order to the *raw* tree before aggregation — which is why every table reports the count it covers without knowing a filter ran, and why the held-out complement is `--instances mipfeas --exclude-instances tuning` rather than a third file that drifts.

`--oracle A B C` adds a best-of-those-configs row (`--oracle-name` renames it on collision, ≥2 participants required): selection is per instance on primal integral at `--time-limit`, **among exactly the seed-collapsed rows the tables already show**, which is what makes the row a true ceiling (headline SGM ≤ every participant's, instance by instance). **Do not "fix" this into per-`(instance, seed)` selection followed by `aggregate_results`**: that collapses picks chosen on primal integral by *median primal bound*, mixing two criteria, and the row can then score worse than a participant while still being labelled a ceiling (~2% of random two-seed trees). The oracle is additive and is held out of `#Win`/`#First` via the `synthetic` set. Instances absent from any participant at any shared seed, or outside the tables' common set, are dropped with the count reported — scoring an out-of-common instance is how selection goes wrong, since `best_known` is built over that set and a missing reference sends `primal_integral` to the dual bound and the tie-break to whoever is named first.

**"Virtual best" in that script is not the oracle** — it is `resolve_reference`'s handling of an observed primal that beats the published `.solu` value, and the module docstring says so; do not merge the two names.

Reference objectives live in `bench/miplib2017-v36.solu`, a verbatim upstream copy. An instance tagged `=inf=`/`=unbd=` is excluded from every table with the exclusion printed, because the gap would otherwise fall back to the best observed primal and enter the SGM as a self-referential zero.

### Release archive

`bench/make_archive.py build <results-tree> --output <dir> --time-limit T` packages a results tree — logs, the `<instance>.opts` each run was given, generated tables, `MANIFEST.json` + `PROVENANCE.md` — and `verify` (wrapped by the archive's own `REGENERATE.sh`) re-derives every table from the archived logs and diffs it, so "regenerable from the archive alone" is checked rather than claimed.

The provenance is *derived*, not asserted: which binary produced a config comes from the `mip-heuristics patch active` marker in each log, since patched and unpatched builds of the same tag have identical version/githash banners. There is exactly one baseline claim — "separately built unpatched binary"; a baseline config whose logs carry the marker is recorded as "ablation on the patched binary — not a vanilla baseline". Instrumentation is recorded both as requested (`log_dev_level` in the `.opts`) and as observed (`[Heur]`/`[Sequential]` tags), because a disagreement is the `--extra-options log_dev_level=1` failure.

`--time-limit` is required because HiGHS takes it on the command line, so it is in no `.opts`. The effective worker count is recorded the same derived way: the harness deliberately does not pin `threads`, so the count appears in no `.opts` and is read from each log's `Thread count N (of M threads)` line into `run.workers_observed` (`parse_highs_log` exposes the same three numbers as `thread_count` / `hardware_threads` / `max_workers` — `thread_count` is HiGHS's pool size and therefore `ExecutionContext::num_workers`, `max_workers` is B&B's own cap, and they are different numbers). **Two distinct values across a tree means it mixes machines and its runs are not comparable**, which warns; neither pinned nor observed warns too. The machine block itself is auto-detected on the *archive* host — hence `--machine-note`.

A campaign yields two archives, headline-timing and `--dev-log` attribution; they are different runs. The release process around it is tracked in the release issue (#166) rather than in this repository — including the ordering constraint that Zenodo's GitHub integration must be enabled **before** the release is created (it does not backfill) and the fact that `.zenodo.json` makes Zenodo ignore `CITATION.cff` entirely.
