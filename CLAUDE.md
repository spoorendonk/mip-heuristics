# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Navigation: LSP → narrow Grep → sliced Read.

# Standards

## Communication Style

Be terse. No preamble. No filler.

## Code Navigation

Prefer narrow queries over full-file reads:

1. **LSP** for symbol questions — `goToDefinition`, `hover`, `documentSymbol`, `workspaceSymbol`. Use before `Read`.
2. **Grep** with `-n` and a small `head_limit` (start at 20); raise only if inconclusive.
3. **Read** with `offset`/`limit` for a slice around the hit. Full-file `Read` is fine under ~200 lines or when structure matters.

Know the symbol → LSP. Know a string, not its location → Grep. Full-file Read is the last mile. This is a preference, not a prohibition: shelling out to `grep`/`rg` is fine when the built-in can't do the job (filtering a pipe like `git log | grep`, or a session without the `Grep` tool). What matters is bounding output, not which binary produces it.

Setup: install `clangd-lsp@claude-plugins-official` plus `clangd` (`apt install clangd`, or from LLVM). `.clangd` points at `build/compile_commands.json`, produced by `CMAKE_EXPORT_COMPILE_COMMANDS ON`.

## C++

- Target C++23. Use modern features (`std::expected`, concepts, ranges, `constexpr`).
- Use `#pragma once`. Minimize header includes; forward-declare where possible.
- **Formatting** is Google, via `.clang-format`. **Naming is not Google** — `.clang-tidy` enforces what this codebase actually does:

  | Kind | Style | Example |
  |---|---|---|
  | Functions (free and member) | `lower_case` | `run_sequential`, `charge_presolve` |
  | Locals, parameters, `const` locals | `lower_case` | `per_worker`, `max_effort` |
  | Private members | **trailing** `_` | `FjWorker::start_`, `seed_` |
  | File-scope / static / class / `constexpr` constants | `k` + `CamelCase` | `kMaxStaleRounds`, `kNumLpArms` |
  | Classes | `CamelCase` | `ScyllaWorker`, `EffortLedger` |
  | Namespaces | `lower_case` | `heuristics`, `fpr` |
  | Files | `snake_case.h` / `.cpp` | |

  `ConstantMemberCase` is deliberately unset: it outranks `PrivateMemberSuffix`, so setting it would reject a `const` private member spelled with this project's `_` suffix. The `.clang-tidy` comments carry the reasoning for each narrowing — read them before changing one.

## Complexity

When a complexity warning fires, don't extract methods mechanically. Ask what the independent responsibilities are and split along those boundaries. If the function is genuinely complex because the domain is, add a comment explaining why and suppress the warning.

## CMake

- `set(CMAKE_EXPORT_COMPILE_COMMANDS ON)` for clang-tidy.
- Use FetchContent for dependencies.
- A single root `CMakeLists.txt`; per-directory files would only add indirection.

## Testing (Catch2 v3)

- `TEST_CASE("name", "[tag]")` with `[tag]` filters, in `tests/`. Not GoogleTest.
- Instances come from HiGHS's own `check/instances/` (path injected as the `INSTANCES_DIR` compile definition).
- `ctest --progress` collapses the running list and `CMAKE_INSTALL_MESSAGE=LAZY` suppresses install chatter. Don't remove these.
- **`[serial]` is a reserved tag**, and it is the *last* resort for a timing-dependent test. `CMakeLists.txt` registers the tagged cases through their own `catch_discover_tests` call carrying `TEST_SPEC "[serial]"` and `PROPERTIES RUN_SERIAL TRUE`, beside a second call taking `TEST_SPEC "~[serial]"` for everything else; the two specs must partition the suite exactly (verify with `ctest -N | wc -l` and a `uniq -d` over the names). Give each call its own `TEST_LIST` name.

  Order of preference when a test flakes under `ctest -j$(nproc)`: **(1) take the clock out of the fixture** — e.g. HiGHS's free-format MPS reader spends `time_limit` as its own *parse* budget, so write the option *after* `readModel`, as `build_bare_mipsolver` in `tests/test_common.h` does; **(2) assert the mechanism** — a one-sided effort bound like `effort < attempt_cap` only gets easier under starvation, so it needs nothing; **(3) only then tag it**, for a wait nothing in the code can bound. **The load-safety of an effort bound is a property of its *shape*, not of the quantity it names**: the *differential* form `effort(T) < effort(5T)` that `tests/test_deadline.cpp`'s `require_clock_bound` uses is two-sided and fails if the longer run is descheduled harder, so it is a (3) case and carries `[serial]` even though it is an effort assertion.

  **Never widen a constant** to stop a flake — a tuned threshold is the same test with a longer fuse. `RUN_SERIAL`, not `RESOURCE_LOCK`: these need an unloaded machine, not mutual exclusion, and neither excludes load from outside ctest, which is why (1) and (2) beat (3) whenever available.

## Development Workflow

```
plan (non-trivial) → implement → test → push to main
```

Nothing formats on save — there are no Claude Code hooks. `clang-format` runs at commit time: `pre-commit` formats the staged C++, applies safe `clang-tidy` fixes, and re-stages the result, so what you commit is canonical even though the file you just edited is not. Don't hand-tune formatting — let the hook normalize it, or run it yourself:

```
.venv/bin/clang-format -i <files>                       # normalize in place
.venv/bin/clang-format --dry-run --Werror <files>       # check only, non-zero if unformatted
```

**Use the venv's clang tools, not PATH.** The pinned 22.1.8 pair lives in `.venv/bin`, which is the exact path `cmake/Lint.cmake` searches; a different major version formats differently and fails the `clang_format` ctest gate. The hooks resolve the venv first for the same reason.

The hooks are **tracked in `.githooks/`** (`commit-msg`, `pre-commit`, `pre-push`, and the sourced `resolve-venv.sh`) — edit them there, not in `.git/hooks/`, which is empty of ours. Git only runs them when `core.hooksPath` points at that directory, and that setting is per-checkout config which cannot be tracked; `cmake -B build` sets it (option `MIP_HEURISTICS_INSTALL_GIT_HOOKS`, ON), leaving an existing `.githooks` value alone and warning rather than clobbering a hooksPath someone else set. To wire a clone up by hand: `git config core.hooksPath .githooks`. `.claude/` is gitignored, owned by this repo, and not part of the published artifact — edit it in place; it holds only permission rules and a statusline. A new Claude Code hook must read its file path and command from the hook JSON **on stdin**, never `$CLAUDE_FILE_PATH` (unset by Claude Code — a hook reading it no-ops silently rather than failing). The clang-format and clang-tidy gates deliberately live outside the hooks, as ctest tests labelled `lint` plus the CI job, so a fresh clone still runs them.

**Never `git push --no-verify` or `git commit --no-verify`** unless asked; a failing hook is a signal, so fix the root cause.

**Do not `git push` while a benchmark is running**: `pre-push` runs the `clean` block, which is `rm -rf build`, so the push deletes `build/bin/highs` out from under every in-flight run — and a harness that stops on a non-zero target exit (irace) loses the whole campaign, not one experiment. `git commit` is safe (`pre-commit` runs tests, not a rebuild). So commit freely during a campaign and push when the machine is idle, or point the run at a copy of the binary outside `build/` (`PLATO_BINARY` / `MIP_HEURISTICS_BINARY` both take a path).

## Git Workflow

Trunk-based, linear history on main. Commit directly to main and push when local gates pass.

Feature branches are optional for larger changes: always branch from main (`git checkout main && git pull` first), never from another feature branch, keep them short-lived, and rebase or squash merge — no merge commits on main.

After a successful push:
- **Close any gh issue the work resolved**: `gh issue close <num> -c "<one-line note>"`, for every issue the push covers.
- **Delete the feature branch** if one was used: `git branch -d <branch>`, plus `git push origin --delete <branch>` if pushed.

## Commit Messages

Conventional Commits; the commit-msg hook enforces format.

- `type: description` or `type(scope): description`
- Types: `feat`, `fix`, `refactor`, `test`, `docs`, `style`, `perf`, `chore`, `build`, `ci`
- Subject ≤72 chars. Focus on **why**, not what.

## Issue Tracking

GitHub Issues, via the `gh` CLI.

- **Default to HTTPS** for GitHub remotes, not SSH.
- **Read an issue** with `gh issue view <num> --json title,body,labels,state,comments`; plain `gh issue view <num>` is deprecated for programmatic use.
- Don't defer work into a new issue unless it is substantial. Fix small follow-ups inline or leave them alone.

Issues get picked up cold, in fresh sessions, often by an agent with no access to this machine. So: keep the body **self-contained** (problem, motivation, acceptance criteria, repro steps); use **no local references** (`/home/user/...`, "see my other checkout" — dead links in a fresh session); prefer **stable external links** (GitHub permalinks, papers, RFCs); and **describe local code by concept, not path**, hinting that the agent can search under `..`, `../..`, or `~/code/`.

## Working Rules

- **CLAUDE.md discipline.** When Claude gets something wrong, fix CLAUDE.md in the same commit. It's a living document — update it whenever better instructions would have prevented the mistake. Keep it **forward-looking**: rules and current behaviour, not a change log. Post-mortem detail, measurements of a past run, and "it used to be X" belong in the issue that owns them.
- **Follow the agreed plan.** If a plan should change, stop and discuss — don't silently diverge. Same outside a written plan: if the current approach isn't working, say so rather than quietly switching strategies. Implement everything specified; no TODO placeholders or stubs unless asked.
- **Match references exactly.** Implementing from papers, pseudocode, or open source: no early exits, iteration limits, size caps, or "optimization" shortcuts that change behaviour. Introduce heuristic approximations only when asked. Implement the edge cases rather than simplifying them away. When in doubt, be faithful and let tests verify. Where the reference is genuinely ambiguous, take a reading, implement it, and record the ambiguity in a comment beside the code (and in `docs/PARAMETERS.md` if it is a parameter) — the deviations recorded below are all of this shape.
- **Don't invent APIs.** Verify functions, flags, and methods exist before using them.
- **Don't ignore type errors.** If clang-tidy or ruff flags something, fix the root cause — don't suppress.
- **Don't use deprecated patterns.** Check current docs, not training data.
- **Performance matters.** Most of this is solvers: profile before micro-optimizing, but don't sacrifice perf for "clean code". Price any micro-optimization against the 4% anchor below.

# Project: mip-heuristics

## Project Overview

Custom MIP (Mixed-Integer Programming) heuristics integrated into the HiGHS solver via a patched fork. The heuristics run during HiGHS's presolve phase and are compiled as object files linked directly into the `highs` library target.

**Reader-facing docs**, kept in sync with this file — update both when the behaviour they describe moves:
- `README.md` — positioning, the `mip_heuristic_suite` table, recorded benchmark results, build options.
- `CONTRIBUTING.md` — build/test/lint commands, the git hooks and how a checkout gets them, the clean-rebuild rule for patch-script changes, the benchmarking rules, the standing code-hygiene bar.
- `docs/REPRODUCIBILITY.md` — what is reproducible and what is not, and the exact PLATO reproduction protocol.
- `docs/RELEASE.md` — how a version is cut and published: the gates, the artifact archive (`bench/make_archive.py`), the DOI wiring and its ordering constraint, and the release checklist.
- `docs/PARAMETERS.md` — every tunable `constexpr`. **Verified by ctest** (`docs_parameter_references`, via `bench/check_docs_refs.py`): renaming a documented constant fails the suite. Entries name symbols, **never line numbers** — line numbers drift on essentially every refactor. Don't reintroduce them.

## Build Commands

```bash
# Lint tools, once per checkout.  `.venv/bin` is the exact path
# cmake/Lint.cmake searches; without this the gates are never registered and
# ctest reports green having linted nothing.  Include pytest — the root
# CMakeLists prefers `.venv/bin/python`, so a venv without it unregisters
# `bench_python_tests` rather than falling back to the system interpreter.
# Include ruff for the same class of reason: both git hooks guard their ruff
# step on `[ -x "$VENV_BIN/ruff" ]`, so a venv without it skips Python linting
# silently while CI still gates on `ruff check bench cmake` — the hooks pass
# and CI goes red.
python3 -m venv .venv
.venv/bin/pip install clang-format==22.1.8 clang-tidy==22.1.8 ruff==0.16.3 pytest

# Configure (from repo root)
cmake -B build -DCMAKE_BUILD_TYPE=Release -DMIP_HEURISTICS_REQUIRE_LINT=ON

# Build
cmake --build build -j$(nproc)

# Run all tests, lint gates included
cd build && ctest --output-on-failure

# Fast inner loop: everything except the two lint gates
cd build && ctest -LE lint --output-on-failure

# Run a single test by name
cd build && ctest -R "execution-mode: flugpl objective" --output-on-failure

# Run tests matching a Catch2 tag
cd build && ./mip_heuristics_tests "[mode-matrix]"
```

The first build fetches and compiles HiGHS via FetchContent, which dominates it. Two things keep the *clean* rebuild that `pre-push` forces cheap:

- **ccache**, wired in `CMakeLists.txt` **ahead of** `include(cmake/FetchHiGHS.cmake)` so HiGHS's own targets inherit the launcher — a target reads the property at creation, so setting it afterwards would cache our four object files and miss the tree worth caching. It does not weaken the clean-rebuild guarantee, because ccache keys on source content and a differently-patched tree misses. `-DMIP_HEURISTICS_CCACHE=OFF` opts out; a missing ccache is a status message, not an error. The launcher does **not** appear in `compile_commands.json`, so `cmake/clang_tidy_gate.py` and `.clangd` are unaffected — re-check that if the CMake version moves.
- **`GIT_SHALLOW ON`** on both `FetchContent_Declare` calls. One visible consequence: git sizes its abbreviated hash by object count, so a shallow tree's banner reads `Githash 04024d70` where a full clone reads `04024d701f` — the same commit at a different width. `same_build` in `check_vanilla_equivalence.py` compares the hash by prefix and `normalize_log` masks its width; `make_archive.py` records one hash per config. **Do not "tighten" either into an equality check.**

**The lint gates are ctest tests**, labelled `lint`: `clang_format` and `clang_tidy`, registered by `cmake/Lint.cmake` over `src/` and `tests/` only. They add roughly 30 s to a full `ctest` run — `ctest -LE lint` is the fast loop while iterating, and the full suite is the gate. `MIP_HEURISTICS_REQUIRE_LINT=ON` turns a missing tool or a wrong major version into a *configure* failure instead of a warning that scrolls past; CI sets it, and so should you, because the default failure mode is silent. Tool versions are part of the contract: clang-format's output changes between major releases, so the pinned 22.1.8 pair from PyPI is what the gate is written against. clang-tidy's own exit status is unusable here — HiGHS's `HighsMipWorker.h` contains a construct clang rejects as a parse error and GCC accepts — so `cmake/clang_tidy_gate.py` wraps it and judges first-party diagnostics itself. **Never work around a tidy finding by widening that wrapper's filter.**

## Build & Test

**`.githooks/pre-push` parses these three fenced blocks by tag** (`clean`, `build`, `test`) and runs them as the push gate, so they are the single definition of a full local run — keep them executable as written and keep the tags. ```

```build

```


GPU acceleration: `-DMIP_HEURISTICS_CUDA=ON` enables CUDA for the PDLP solver used by Scylla. It **requires `CUDA_HOME`** to be exported (HiGHS's `FindCUDAConf.cmake` derives `CMAKE_CUDA_PATH` from it and uses that for the cudart/cublas/cusparse `find_library` hints and for HiGHS's CUDA include directory), and it **fails the configure** if nvcc or `CUDA_HOME` are missing, or if the `HConfig.h` HiGHS generates doesn't come out GPU-enabled — it does *not* fall back to CPU. That's deliberate: GPU vs CPU is a compile-time `#ifdef CUPDLP_CPU` in HiGHS's `CupdlpWrapper.cpp` with no runtime override, so a silent fallback yields a CPU binary indistinguishable from a GPU one at the command line. Build GPU into a separate tree (`cmake -B build-gpu -DMIP_HEURISTICS_CUDA=ON`) and confirm with `ldd build-gpu/bin/highs | grep -E 'cudart|cublas|cusparse'`. Omit the flag for a CPU build.

## Architecture

**Integration model**: Heuristics are compiled as a static object library (`mip_heuristics`) whose objects are injected into the HiGHS `highs` target. The HiGHS source is fetched at build time (v1.15.1) with patches applied from `third_party/highs_patch/`. Heuristics access HiGHS internals directly via `HighsMipSolver&`.

**No backward compatibility with older patch versions.** `apply_patch.cmake` refuses any HiGHS tree whose `mip-heuristics patch version` marker is not the current `PATCH_VERSION`, and does not attempt an in-place upgrade — no retired-identifier list, no rewriting an older option layout. **Bump `PATCH_VERSION` on any change to inserted text and clean-rebuild; that is the whole contract.** The marker lives in `HighsOptions.h`, so it speaks only for that file — the surviving probes are the ones for markerless files: `HighsMipSolver.cpp`, whose `heuristics::run_presolve` / `fpr_lp::run` idempotency sentinels are present in every layout the call sites have ever had, and `HighsCliqueTable.h`, whose two const clique-list accessors are likewise markerless. Retiring an option that appeared in an inserted *call site* means updating that file's probe to name it; retiring one that only appeared in `HighsOptions.h` means nothing but the version bump. The same stance applies to the harness: results trees must use the `<config>/seed<N>/` layout, and config names have no aliases.

**Bumping the HiGHS tag**: HiGHS renames `advanced` options across minor versions with no deprecation shim (`pdlp_scaling` → `pdlp_scaling_mode` and `pdlp_e_restart_method` → `pdlp_cupdlpc_restart_method` at v1.14.0). Every `Highs` instance we build sets `output_flag=false`, so a rejected `setOptionValue` is completely silent — it reports failure only through the return status. After a bump, grep for `setOptionValue` and check each name against `_deps/highs-src/highs/lp_data/HighsOptions.h`, and prefer routing writes through a status-checking helper (`set_option_or_die` in `contested_pdlp.cpp`). Verifying that an option *exists* is not enough: check that the code path you're on actually reads it (e.g. `pdlp_scaling_mode` is consumed only by HiPDLP, never by cuPDLP-C).

**Heuristic entry points** — each has a standalone `run()` that HiGHS calls during presolve.

### `fpr` — Fix, Propagate, and Repair

DFS tree search that fixes integers, propagates bounds, repairs the *partial* assignment at every node the fixing or propagation refutes, backtracks on infeasibility, and finally runs WalkSAT/RepairSearch on the leaf.

`fpr_core.cpp` exposes two APIs: the one-shot `fpr_attempt` (scylla / fpr_lp / one-shot tests) and the `fpr_attempt_begin` / `fpr_attempt_step` / `fpr_attempt_finish` lifecycle that lets `FprWorker` pause an in-flight DFS at the per-call budget gate and resume it, with state in `FprAttemptState` + `FprScratch`. Multi-attempt looping inside `run_attempt` lets fast workers fill the slice with new attempts, rotated through `kInitialFprConfigs` per `(worker_idx + attempt_idx)`.

Sub-algorithms: `prop_engine` (bound propagation, forward propagate plus a domain PQ for dynamic-var strategies — `repair_search` requires `e_pq_mark` threading on `RepairSearchNode` to keep the PQ consistent across its secondary backtracks), `walksat`, `repair_search`, `repair_walk`, `fpr_strategies`.

**Propagation results.** `PropEngine::propagate` returns a `PropResult` four-state, not a `bool`: a per-call matrix-access budget (`kPropagateBudgetPerNnz * nnz`) can exhaust before the worklist drains, and the fixpoint also polls the wall clock every `kPropagateDeadlinePollWork` counted units. `kBudgetExhausted` and `kDeadlineExpired` are truncated-but-sound fixpoints, not verdicts: **every caller prunes only on `kInfeasible`**. The two truncations are **not aliases** — budget exhaustion means "this got expensive, carry on", expiry means "the solve is over" — so each caller decides what expiry means *there*: the DFS in `fpr_attempt_step` breaks out of the node loop at once, pushing the node back so the paused stack matches a pre-node deadline break, while `sync_changes` and `apply_branch_to_r` deliberately do **not** signal it outward, because their `bool` can only say "prune" and the RepairSearch loop already polls the same deadline once per node.

The engine takes its `Deadline` through `set_deadline`, not its constructor, and **both arming sites (`acquire_engine`, `repair_search` for E and R) must call it on the *reuse* path as well as on construction**, since both cache an engine across attempts. A null `Deadline` sets the cadence counter to `SIZE_MAX`, so an un-armed engine reads no clock at all.

**Repair runs in the tree, on the partial assignment** (`src/repair_walk.{h,cpp}`, Fig. 1 lines 7-8, at *every* node whose processing left the problem infeasible). Four load-bearing properties:

1. **Violation is the activity range, not a solution vector.** A row is violated when the interval `[m_i, M_i]` its current domain admits is disjoint from the row's bounds — no completion satisfies it — and the violation is the distance between them. Those are the activities propagation maintains, so `fpr_attempt_begin` calls `E.init_activities()` for every `mode_repairs` mode, not only `kLoosedyn` (arming them moves no value selection: `choose_value` reads activities on the `kLoosedyn` branch alone). The same measure is what makes `Apply(fixing, P)` able to refute a node (Fig. 1 line 4), via `any_violated_row_in_column` — without it `dive`, where propagation never runs, could not repair at all, since `PropEngine::fix` fails only on the column's own domain. It also covers propagating modes, where `propagate` skips a row with no unfixed columns. Only the fixed column's rows are scanned, and the check is gated on `do_repair`. **Deliberate deviation**: damage and the best-state comparison sum violation *magnitudes*, not counts — the paper says both; recorded in `docs/PARAMETERS.md` beside `repair_noise`.
2. **A move is a *shift*, and what shifts is the node's domain.** Column `j`'s current interval translates by `s`, keeping its width, through `PropEngine::shift_domain` — a third operation beside `fix()` (refine within the current domain) and `refix()` (override with a singleton). **Enlargement is not a legal repair move**, so a shift is bounded by how far the interval can slide inside the column's *structural* bounds, and a column with an infinite endpoint cannot shift. A fixed column's interval is its `val`, not `[lb, ub]`, because `fix()` leaves those wide. Scoring needs no engine call: translating `j`'s interval by `s` translates both activity endpoints of every row containing `j` by `a * s`.
3. **Every change goes through `E`, so its undo stacks are the snapshot.** The soft restart (back to the best state every `kSoftRestartPeriod` shifts) and the end-of-walk restore are a `backtrack_to` on a four-integer mark; the DFS's backtrack unwinds a repair with its node, and a `step` paused at the budget gate resumes with the repair committed. The tabu list of the last `kTabuLength` shifts survives a soft restart (the paper does not say either way). **Do not "optimize" the restart into an incremental violated-set repair** — an earlier revision did, provably equivalently, and no test could reach it, because the end-of-walk restore masks every observable difference a soft restart makes.
4. **The trigger is `PropResult::kInfeasible` and nothing else.** Its effort valve is **internal** (`kRepairWalkBudgetPerNnz`) rather than a caller argument, because neither number a caller could pass bounds `E.effort()`: the per-call DFS slice is already spent by the time propagation refuted the node, and `FprConfig::max_effort` does not bound the counter. A caller cap turns every repair past the crossing into a no-op that still pays its entry scan — on the long attempt on the hard model, the case repair exists for.

**Phase 3 (leaf-time repair) takes no caller cap either**, for the same reason: `repair_search` is governed by `cfg.repair_iterations` (its propagation fixpoints already answer to `kPropagateBudgetPerNnz`) and `walksat_repair` by `cfg.walksat_iterations` plus `kWalkSatBudgetPerNnz`, which gates the *delta* the call charges because its `effort` parameter is a caller's running total. `FprConfig::max_effort` survives only because the one-shot `fpr_attempt` wrapper reads it as its single DFS gate; under the lifecycle API `run_attempt` leaves it at `SIZE_MAX`. **The scope of both is wider than FPR**: every `mode_repairs` leaf walk — FPR, the two `mode_repairs` Scylla chains (`kFprConfigs[2]` `kDive`, `[3]` `kDfsrep`) and the six `mode_repairs` `fpr_lp` arms of ten (`ZerocoreDive`, `ZerocoreDiveprop`, `ZerolpDiveprop`, `Cliques2Diveprop`, `LpDive`, `LpDiveprop`).

**Cost to know**: a refuted node costs one O(`nrow`) scan (nothing upstream maintains a violated-row set; within the walk it is incremental), and a soft restart pays it again. It is charged to `E.effort()`, so a fixed effort budget buys fewer DFS nodes than a no-repair build would.

**Fig. 1 does not prune an infeasible node in a non-backtracking mode**: lines 9-10 backtrack only `if backtrackOnInfeas` and line 11 branches regardless, so `dive`/`diveprop` carry an unrepaired node to the bottom. **At the bottom they set `found_complete` even when the leaf is infeasible** — Fig. 1 ends at line 16, and Phase 2.5's fill plus the leaf-time `walksat_repair`/`greedy_1opt` are a post-process whose precondition is "a leaf with every integer fixed", never "Fig. 1's `infeas` was false".

**There is one verdict site.** `infeas` feeds the repair call and the backtrack decision and nothing else; what is *returned* is decided solely by `fpr_attempt_finish`'s point re-check over every row. That is what makes `any_violated_row_in_column`'s one-column scan sound — a correct definition of `Apply`'s verdict, an incorrect one of "the problem is infeasible". `infeas` is non-global for two further reasons the same re-check covers: Phase 1's batch fixings bypass `Apply`, and a repair's collateral damage on rows no later column touches is never re-reported. The leaf-time walk is a genuine second chance, not a duplicate: it scores a *point* where the in-tree walk scores activity ranges, from its own RNG stream.

`kRepairSearch` is deliberately **not** in the tree (`mode_repairs` excludes it): moving it in needs `repair_search` to work on a partial assignment, which is open.

**A failed attempt still hands back its point.** Every failure return of `fpr_attempt_finish` carries a `solution` of length `ncol` with every integer column integral and inside `[col_lb, col_ub]`, while `found_feasible` stays false — Sect. 2.3's "always produces an integer-feasible, but not necessarily LP-feasible, solution". So **Phase 2.5's fill runs on every path**, and the `!found_complete` path is charged the fill plus the `ar_index.size()` row rebuild. Phase 2.5 does **not** buy Phase 3: its precondition is still `found_complete`. `HeuristicResult::infeasible_point` is the factory and leaves `objective` at infinity — **no caller may read it**. `found_feasible` still gates every `IncumbentSink::offer` site. On the two Phase 3 paths the point is `scratch.solution` **as Phase 3 left it**, not the pre-repair leaf. Two consequences: the fill writes no counter, so **it is wall time no effort gate can see**; and the LP-reference arms draw RNG inside it (`val_lp_based`), where `kBadobj`/`kLoosedyn` draw nothing.

**The leaf-time repair takes the global bounds, and that is correct**: Phase 2.5 has produced a complete assignment, so every column's effective domain is the singleton at its value and the paper's rule for a value shift is the global-bound clip verbatim. "Against the node's current domain, not the global bounds" is about the *in-tree* call. A test asserting only on the returned `HeuristicResult` cannot see this, which is why `tests/test_repair_walk.cpp` asserts on the engine's per-column state *between* the dive and Phase 3.

**RepairSearch** (Fig. 5, Sect. 5.1):

- `sync_changes` (line 13) re-fixes an already-fixed column when R's domain rules it out — the binary-swap mechanism RepairSearch exists for — and fixes a disjoint domain to R's nearer endpoint, via `PropEngine::refix`: a `fix()` validating against *structural* bounds, since both cases target a value outside the current domain by construction.
- **The node loop is a DFS with a gated jump, not a best-first search.** Lines 18-19 backtrack to the best open node only once `progress_threshold` consecutive nodes have failed to improve the best total violation. **The jump runs after the children are pushed**, which is not the figure's line order and is deliberate: `Q` is a LIFO stack, so a promotion made where lines 18-19 sit is buried under the children and resurfaces only once their subtree is exhausted — the very "inability to escape a wrong subtree" the jump exists for. A node reaching neither push never jumps.
- **A jump discards the open nodes beneath it, and must.** Each node restores its parent state by replaying an undo trail down to seven marks, sound only while the marks along `Q` are non-decreasing front-to-back so a pop always unwinds *downward*. `backtrack_best_open` (declared in `repair_search.h`, unit-tested directly, because a whole-search outcome cannot separate "dropped the subtree" from "permuted it to the back") drops every open node after the promoted one whose marks are strictly deeper in **any** of the seven components, keeps the ones whose marks *equal* it (the alt/pref pair pushed at the same parent state, sharing its trail prefix), and only then swaps it to the back. That is exactly the completeness Sect. 5.1 says the jump gives up; a permutation keeping the deeper nodes would cost no completeness at all, which is the tell. **Clamping the backtracks to the live stack size instead hides the symptom, not the bug** — after a jump the trail beneath a deeper node's mark has been *rewritten*, so even a non-growing restore reinstates an unrelated state.
- `RepairSearchStats::mark_overshoots` is checked at the pop site over all seven marks and **must stay zero**: it is the Release-mode observable of that invariant, since the tests build `-DNDEBUG`. `nodes_abandoned_by_jump` counts what a jump gives up.
- `progress_threshold` is a parameter defaulted to `kRepairProgressThreshold` (`repair_search.h`; no option behind it). `fpr_core.cpp` names no value, so the production value lives in one place; `tests/test_repair_search.cpp` runs one model at both ends of the axis and pins the defaulted call against an explicitly-valued one.
- **The post-loop restore is not Fig. 5 line 27**, and its comment says so and says it is a choice: line 27 is implementable verbatim here *because* of the mark-ordering invariant. What is restored instead is the best `(solution, lhs_cache)` snapshot line 17 took — the best node *visited*, which is at least as good as the best still *open* under line 17's own measure. Nothing is restored when `repair_track_best` is false. `RepairSearchStats` is the seam the tests read; production passes `nullptr`.
- **`MoveToDisjunction` branches on the shifted interval, and each disjunction is a point split.** With `[a, b]` = **D translated by the move's shift** and R's domain `[c, d]`, `l = a - c`, `r = d - b`: if `l <= r` impose `x_j <= b \/ x_j >= b`, else `x_j <= a \/ x_j >= a`.
  - Building `[a, b]` from D itself instead makes both children re-impose a bound R already holds, leaves `sync_changes` nothing to transfer, and moves nothing on a general-integer column. What shifts is the *interval*, so it keeps D's width; a fixed column's D is the singleton at its `val`.
  - **Both sides naming the same endpoint is not a printing error.** `x_j <= v \/ x_j >= v` covers the line and leaves the shifted interval intact in exactly one child; choosing which endpoint to split at is the only thing the two gaps are for. The "obvious typo" fix — the overlapping pair `x <= b \/ x >= a` — is a cover **with a hole**: `(a, b)` is in neither child, and the move value sits exactly there whenever the point is interior to D.
  - Which child is *preferred* is not in the text; we take the one holding `[a, b]`, by analogy with the binary case.
  - **The containment is a deviation, not a fact**: `walksat_select_move` clips a shift to structural bounds rather than to R's domain, so `[a, b]` can leave `[c, d]` and is clipped back in. Reachable only at zero width with a point drifted off a fixed column's value; at positive width `width(D) <= width(Dr)` forces the selected endpoint to stay inside.
  - Downstream, the clamp turning a bound branch into a point move reads the interval **E holds**, not `[lb, ub]`, since `sync_changes`' intersection case commits through `PropEngine::fix`, which leaves the bounds wide.
  - `move_to_disjunction` is declared in `repair_search.h` and unit-tested directly, for the reason `sync_changes` is: a whole-search outcome cannot separate two split points, because the point ends up clamped to whatever propagation implies. `RepairSearchStats::bound_branch_moves` counts nodes where a bound branch moved the point.

**`FprConfig::strategy` is always required**: `choose_fix_value` has one path, the paper's variable ranking + value selection (`fpr_strategies`'s `choose_value`), which reads `FprConfig::lp_ref` for the LP-based value strategies (`kZerocore`/`kZerolp`/`kCore`/`kLp`) — the single reference-point mechanism into fix-and-propagate.

`fpr_attempt`/`fpr_attempt_begin` carry **no seed input**, and adding one back would be inert: every write into the engine's solution array is overwritten by `fix()`/propagation auto-fix or by the Phase 2.5 fill before anything reads it.
### `fpr_lp` — LP-dependent FPR (paper Classes 2–3)

Uses the root LP solution. Called during the B&B dive (after RENS/RINS), not presolve. Draws from the **same LP-iteration budget as RENS/RINS** (`mip_heuristic_effort` envelope) and charges its work back.

Gated by `heuristics::effective_flags(...).fpr_lp` **and** by `mip_heuristic_fpr_lp_effort > 0`. **Both gates return from the same place** — above every read and write of `heuristic_lp_iterations` / `total_lp_iterations`, which feed `moreHeuristicsAllowed()` and therefore decide whether RENS and RINS run, so a disabled `fpr_lp` leaves those two exactly as they were; that is what makes an `fpr_lp` ablation an ablation of `fpr_lp`. `tests/test_fpr_lp.cpp` pins the two spellings of "off" (zero effort, absent token) as the same solve — objective, node count and LP-iteration total. It skips entirely while `parallelLockActive()` — multi-worker B&B under `parallel=on` — because those counters are shared and it has no worker-local flush path.

It runs arm-aligned parallel workers (`w % kNumLpArms`): each of `num_threads` workers is bound to an LP arm from the curated Class 2/3a/3b list, excess workers wrapping the arm list with distinct seeds. Each arm is one `LpArmInfo` record in `kLpArmTable` (`src/fpr_lp.cpp`) carrying its `(strategy, mode)` pair *and* the reference-vector class (`LpRefClass`) its strategy is defined against — analytic center (Class 2), zero-obj vertex (Class 3a), or full-obj LP (Class 3b) — so the arm-to-class assignment is derived from that one record rather than kept in sync across parallel per-class arrays that can silently disagree. `fpr_lp::lp_arm_table()` is what `tests/test_fpr_lp.cpp` asserts on ("every LP arm's reference class matches what its strategy needs").

**That table-level test is only half the binding.** `build_setup` still has to turn a `ref_class` into a pointer, through **`select_ref` — a small pure function, not a switch inlined at the call site, with no `default` case and no pointer pre-assigned before the switch** — with its own test exercising every enumerator directly (`"fpr_lp: select_ref returns the pointer its LpRefClass names"`). `-Werror=switch` on the `mip_heuristics` / `mip_heuristics_tests` targets turns an unhandled enumerator into a compile error, for this switch and every other one in our own code.

**`LpArmInfo`/`LpRefClass`/`lp_arm_table()`/`select_ref` live in `src/fpr_lp_arms.h`, not `fpr_lp.h`**: the patch inserts `#include "fpr_lp.h"` straight into HiGHS's own `mip/HighsMipSolver.cpp`, compiled at HiGHS's own `CMAKE_CXX_STANDARD 11` (not this project's C++23), so `fpr_lp.h` stays a bare forward declaration of `HighsMipSolver` and **nothing it includes may drag in `fpr_strategies.h` / `heuristic_common.h`** — both use C++17 `inline constexpr` and C++14 multi-statement `constexpr`, which fail to compile under `-std=c++11`.

Its per-dispatch `build_setup` — CSC transpose, two reference LP solves, one `compute_var_order` per arm — is sequential on the dispatching thread and sized by nothing, so it is deadline-gated between arms and around each solve, and **a bail owes the envelope**: a setup abandoned after a reference solve has already spent LP iterations that must still be booked. It returns a `SetupResult` (the optional setup, `lp_iterations` spent whether or not one came back, and `deadline_bail`), and `fpr_lp::run` charges through `charge_dive` on exactly one of two disjoint paths — the bail books `effort=0` plus whatever the solves cost and reports `abandoned_setup=1`; the normal path books once at the end. The model-shape and LP-status skips consume nothing and stay silent. **Poll the clock rather than testing the returned LP vector**: the `ac_ptr`/`zv_ptr` fallbacks read an empty vector as "LP failed, use the full-obj solution", which would mask an expiry. Nothing is cached across dives, so no path can charge another's work.

`dive_budget` is a **free function with its own test**, not four lines inlined in `run`, because no assertion on a solve separates "the share scaled the budget" from "the budget happened to land there". It computes `share * min(headroom_units, cap_units)`, with the cap `vanilla_effort_budget(nnz, mip_heuristic_effort)`. **The share multiplies the whole `min`, not the headroom term inside it** — otherwise the per-call cap binds at every share and the option cannot express a budget that never binds, the one thing its `1e6` ceiling exists for. Overdrawing the envelope at a large share is self-correcting rather than a leak: the charge-back depletes the same counters the headroom is computed from, so the next call sees none and skips.

`fpr_lp` has no patience option and keeps `worker_budget >> 2` with its own improvement signal.

### `fj` — Feasibility Jump

HiGHS's own FJ implementation, run on continuous parallel workers — a delegating wrapper, but not a *thin* one: `apply_patch.cmake` corrects two upstream defects in `feasibilityjump.hh`, inherited from the SINTEF reference and present in HiGHS v1.15.1 and on master.

1. **The negative-coefficient jump value.** `JumpMove::updateValue` divides both endpoints of a row's bound interval by the variable's coefficient, which reverses the inequality when the coefficient is negative; without a swap `validRange.first > validRange.second` fires unconditionally and the row is dropped, contributing neither a critical value nor a slope. Paper eq. (5)/(6) give the critical value an explicit negative-coefficient case and Algorithm 1 accumulates the pre-bound slope by that sign, so the fix is one conditional swap placed **before** the integer ceil/floor — after it, `floor` on the true lower endpoint yields a value one below the smallest that satisfies the row. What degrades is the **move — the (value, score) pair — not the scoring rule**: `resetMoves` builds `candidateLhs` from `move.value`, so it scores the move `updateValue` just chose. Damage concentrates on general integers and continuous columns.
2. **The sign of the objective term in the move score.** Sect. 2.6 makes the score a *minimized* sum; the constraint terms are improvement-positive, `selectVariable` takes the maximum, `updateGoodMoves` calls a move good when its score is positive, and both live callers hand `addVar` coefficients already multiplied by the model sense — so upstream's spelling scores an objective-*worsening* move positively. It is negated at **both** sites that spell the term, `resetMoves` (recomputed) and `updateWeights` (applied incrementally on the no-violated-constraint branch): a sign disagreeing between them would drift the scores apart on every weight bump.

Pinned by `tests/test_fj_jump_value.cpp` (which drives `JumpMove` directly as well as the solver, because two cases pin the *slope* half, whose models FeasibilityJump cannot satisfy) and `tests/test_fj_objective_sign.cpp`. The sign test covers `resetMoves` and not `updateWeights`, because the two disagree only by drift. **The patch's post-check asserts on both sites and on the absence of either `+=` spelling; it refuses a half-applied patch and is a spelling check, not a substitute for a test.**

The patch also **drops FJ's per-bump `Reached a local minimum.` log line**, which was ~99.8% of a `log_dev_level=3` run's log volume and made a clock-bound traced FJ dispatch a different heuristic from an untraced one. What remains at level 3 is FJ's periodic table and our own two lines — closer, but still not the same run, which is why `run_benchmark.py` leaves level 3 off behind `--dev-log`. A patched binary's FJ output no longer matches vanilla's at level 3, one of the reasons `off` is an ablation and not a vanilla proxy.

**FJ's per-worker solver construction is unbounded** — `createRowwise` plus `addVar`/`addConstraint` plus `init`'s `resetMoves`, before the first callback can fire — and is deliberately out of scope; a deadline in the callback cannot bound it.

MIP neighborhood search, run on continuous parallel workers.

### `scylla` — feasibility pump (Mexi et al. 2023)

Alternates PDLP approximate LP solves with FPR rounding, progressive objective blending, and cycling perturbation. Runs N independent pump chains sharing a single `ContestedPdlp` instance so only one PDLP solve is in flight at a time. Workers that can't grab the PDLP mutex fall back to rounding against the most-recent *stale* snapshot so N-1 chains stay productive during a peer's solve, bounded by `kMaxStaleRounds` per worker before forcing a blocking solve.

Each chain owns its own warm-start, α_K decay, cycle history, RNG, and static FPR rounding strategy (`kFprConfigs[w % N]`). **Every chain's value strategy is `ValStrategy::kLp`**, so each chain's rounding reads the pump's PDLP iterate `x_bar` via `FprConfig::lp_ref` (Algorithm 1.1 line 12). Variable strategy, framework mode and RNG stream stay diverse per chain — three distinct variable strategies across the four entries, `kTypecl`/`kLocks`/`kLocks`/`kLR`, the latter two named `kStratLocksLp`/`kStratLRLp` in `fpr_strategies.h` as Scylla-specific, non-Table-3 combinations.

The variable *order* stays `x_bar`-free: precomputed once per dispatch on the dispatching thread (`scylla::precompute_config_var_orders`), because a per-iteration order would reach the live clique table from inside the parallel pump loop.

**Cycling detection is near-dead in the fractional regime, and that is sanctioned rather than a defect.** `val_lp_based` is probabilistic (Sect. 4.2), so away from an integral `x_bar` the same iterate no longer maps to the same `x_hat` and `pump::detect_cycling`'s exact-vector match rarely fires, leaving line 14's perturbation near-dead there; it re-arms near convergence, where `frac < 1e-10` makes the rounding deterministic. The randomized in-tree repair on the two `mode_repairs` chains adds a second source of the same effect. Know this before a cycling investigation starts from scratch.

**A failed rounding still advances the pump.** Lines 14-16 run unconditionally — a feasibility pump is *defined* by being pulled toward the rounded point whether or not it is feasible, and line 13 returns only when it is MIP-feasible — so `detect_cycling`/`perturb`, `record_cycle_entry`, the `alpha_K_` decay, `compute_pump_objective` and `++K_` all run on a failed round; otherwise the chain re-solves a byte-identical LP with a byte-identical `modified_cost` and makes no progress. The only `solution.empty()` guard left is the degenerate `ncol == 0 || nrow == 0` short-circuit. Consequences to know rather than fix: `perturb` draws from `rng_` on failed-rounding cycles, and the `pdlp_stall_count_` retirement a repeated identical LP used to produce mostly disappears. No pool restart is fed into the rounding call.

## Dispatch and parallel infrastructure (`src/`)

- `mode_dispatch` — top-level presolve entry point. Reads `mip_heuristic_*` options and runs the fixed chain via `run_sequential`: FJ → FPR → LocalMIP → Scylla, each with its own effort budget and each on continuous parallel workers. The chain is a `constexpr` four-entry `HeuristicConfig` table (`{name, source_tag, flag, effort, budget_is_per_worker, patience, run}`, `effort` a pointer-to-member naming that heuristic's effort option) and `run_sequential` is a filtered loop over it — **adding or reordering a heuristic is a table edit**. There is one parallel runner. Reproducible runs come from `threads=1` plus a fixed `random_seed`; no new option.
- `heuristic_context.h` — the common runner contract. All four heuristics expose `size_t run(const ProblemView&, const HeuristicBudget&, ExecutionContext&, IncumbentSink&)`. `ProblemView` is the model + CSC transpose + derived `ncol`/`nrow`/`nnz` + a copy of the incumbent, built **once per dispatch** by `make_problem` and shared by the chain (`mipdata`'s row-major buffers are frozen by `runSetup()` before dispatch).
  - **Workers must read `problem.incumbent`, never `mipdata->incumbent`.** Submission is immediate, so a peer's accepted solution runs `addIncumbent` — whose `incumbent = sol;` rewrites that buffer element-wise and reallocates it on the empty-to-sized transition — while a worker indexes the live vector. Read it *after* the pool, never instead of it: every accepted solution goes through the pool first, so `copy_best` is the thread-safe way to see a peer's find, and a worker rebuilt mid-dispatch (FJ does this on staleness) that skipped the pool would silently lose it.
  - **Anything else a worker reads out of `mipdata` must be frozen by `runSetup()` or snapshotted the same way.** `fpr_lp` keeps its own copies in `LpFprSetup`; `seed_pool` reads the live vector only because it runs on the dispatching thread before any worker starts. `ProblemView::binary` is the second such snapshot: `addIncumbent` also runs `getDomain().propagate()` and `redcostfixing.propagateRootRedcost`, which tighten the root bounds `HighsDomain::isBinary` reads, so workers classify columns from the snapshot — LocalMIP via `WorkerCtx::is_binary`, FPR/Scylla/fpr_lp via `FprConfig::binary_mask`, which any caller inside a parallel region must set.
  - **The one live `isBinary` read left is `bucket_by_type` in `fpr_var_order.cpp`, reached only through `compute_var_order`, and every `compute_var_order` caller must run on the dispatching thread** — `fpr::precompute_var_orders`, `fpr_lp`'s `build_setup`, `scylla::precompute_config_var_orders` — because `addIncumbent`'s `extractObjCliques` reallocates the clique table concurrently. **Any new caller is bound by the same rule.**
  - `HeuristicBudget` is one heuristic's `total`/`per_worker`/`attempt_cap`/`stale`/`worker_stale` split from `make_budget`, which takes the staleness ceiling as an argument rather than deriving it. `ExecutionContext` carries worker count, base seed, and the two termination predicates. `fpr_lp` takes only `make_exec`/`make_budget`.
- `incumbent_sink` — the only path from a worker to a solution. Owns the `SolutionPool`, the mutex around HiGHS's non-thread-safe `trySolution`, and the `kSolutionSource*` tag; workers call `sink.offer(obj, sol)` and never name their own tag. `run_sequential` re-tags via `set_source` between heuristics (legal only there — every parallel region has joined). Its atomic `accepted()` counter moving across one dispatch is the `found` field of that heuristic's `[Heur]` line, since a worker's return value is its effort and nothing else.
- `effort_ledger` — the only place *in `src/`* that writes `heuristic_effort_used` or emits the `[Sequential]` / `[Heur]` lines (the patch adds one further `heuristic_effort_used +=` inside HiGHS's own `feasibilityJump()`, live only at `suite=off`, emitting no log line). `charge_presolve` for the chain; `charge_dive` for `fpr_lp`, which additionally depletes the RENS/RINS LP-iteration envelope. `EffortLedger::now_s()` is the solver's own clock (`HighsMipSolver::timer_`), not a raw `steady_clock`, so `[Heur] start_s/end_s` share an origin with HiGHS's display-line time column. **Nothing else in `src/` writes an upstream `HighsMipSolverData` counter.**
- `worker_base.h` — `AttemptResult` (one attempt's effort + improvement flag) and `WorkerBudgetState` (per-worker effort / staleness / budget bookkeeping, embedded by composition into all four workers — `FprWorker` arms only the staleness half, leaving `total_budget` at SIZE_MAX because the whole-dispatch ceiling belongs to the runner).
- `opportunistic_runner.h` — the generic continuous parallel loop every heuristic runs on.
- `scylla_worker` / `pump_common.h` — Scylla worker class and shared feasibility-pump primitives.
- `fj_worker` / `fpr_worker` — the FJ and FPR worker classes. `FprWorker` is declared inline in `src/fpr.cpp`; there is no `fpr_worker.*` file.

### `contested_pdlp`

Mutex-guarded `Highs` PDLP wrapper shared by all Scylla workers. One-shot `solve(modified_cost, warm_start, epsilon)` holds the mutex for the full `changeColsCost → setSolution → run → getSolution` path, guaranteeing at most one PDLP solve is in flight (critical for cuPDLP GPU state); the in-flight counter is debug-asserted == 1 inside the critical section. `try_solve_or_snapshot(...)` is `try_lock` + fresh solve on success, or a lock-free `std::atomic<std::shared_ptr<const Snapshot>>` read of the most-recent completed solve on contention.

- **The `epsilon` argument is the pump's single stopping error and must reach all three parameters cuPDLP-C's termination check reads** — `D_PRIMAL_TOL`, `D_DUAL_TOL`, `D_GAP_TOL` — because cuPDLP-C terminates on their conjunction and relaxing a subset relaxes nothing.
- **It gets there through one write to `kkt_tolerance`, not three writes to the tolerance options, and that is not stylistic.** `primal_feasibility_tolerance` and `dual_feasibility_tolerance` are not private to the PDLP solve: `HPresolve` reads both verbatim in ~100 places (`weaklyDominatedCol` fixes a column whenever `direction * dualBound >= -dual_feasibility_tolerance`, and the pump's modified costs are O(0.1–1)), so writing them presolves a *different LP* rather than solving the same one loosely. `kkt_tolerance` is resolved into feasibility thresholds only as *function-local* variables in `HighsSolution.cpp`'s KKT checks. The route also keeps HiGHS's own KKT accounting consistent with the solve, since both read the same constant. Domain `[kMinimumKktTolerance = 1e-10, kHighsInf]`, so no schedule value is clamped.
- Its cost is that it leans on an upstream "if changed from its default" branch — the cross-version fragility the HiGHS-bump paragraph warns about. So `tests/test_contested_pdlp.cpp` pins the **effect** (a looser epsilon takes strictly fewer PDLP iterations), not the option name, with a **third arm** requiring the loose epsilon to also beat an untouched-`kkt_tolerance` solve, so a bump re-conditioning the override to fire only *below* the default cannot strand the loose end silently.
- `SolveResult::model_status` is public and stays epsilon-dependent in principle; `absorb_fresh_solve` retires on `kError`/`kInfeasible` alone, so a future caller testing `== kOptimal` should read this first.
- **The wrapped instance never presolves**: the constructor writes `presolve` = `off` through `set_option_or_die`, and the reason is the pump's warm start, not presolve's cost. `optimizeModel` cannot take its presolve-skip branch under `solver=pdlp`, and on `kReduced` HiGHS calls `solveLp(reduced_lp, ...)` with the **full-model** solution object while `solveLpCupdlp` resizes it to the *reduced* LP's dimensions with `value_valid`/`dual_valid` unchanged — so `PDHG_PreSolve` read a truncated prefix of our warm start, landing the previous iterate on the wrong columns and rows. `presolve=off` is well defined here (`runPresolve` returns `kNotPresolved`, no postsolve, `getSolution()` in the full column space, which is what `absorb_fresh_solve` stores and `ScyllaWorker` asserts on). **Consequence**: a `pdlp_iters == 0` return is *reachable*, so `pump::kMaxPdlpStalls` is a live retirement path — three in a row should stay hard, since the modified cost changes every round, and `tests/test_deadline.cpp`'s "a clock-bound Scylla dispatch spends its whole limit" is the standing check. An instance that does retire early is a separate issue about the stall rule, **not a reason to put presolve back**. The surviving design option (presolve once in the wrapper and keep the pump in the reduced space, mapping the iterate ourselves) is recorded in `docs/PARAMETERS.md`.
- **The solve's time limit is not an argument**: the wrapper owns the `Deadline` and reads what is left of it *inside* the lock, because a caller computes a value and then blocks for the length of a peer's whole solve. A solve entered past the deadline returns an empty `SolveResult`, whose `kError` default retires the chain.
- **`solve_locked` calls `highs_.zeroAllClocks()` inside the lock and before the `time_limit` write**, because that limit has two consumers with different clock origins: cuPDLP-C charges from entry to `PDHG_Solve` (this solve), but `Highs::runPresolve` compares `options_.time_limit` against the *wrapped instance's* clock, which accumulates across every solve of the dispatch. Without the zeroing, a shrinking remaining time meets a growing accumulated one about halfway through the dispatch and every later solve returns `Time limit reached` with 0 PDLP iterations, retiring the chain. **Do not "fix" this by widening the limit handed to the sub-solver** — that repairs the ratio while leaving presolve budgeting against a growing origin *and* over-granting `D_TIME_LIM`; the ratio test in `tests/test_deadline.cpp` is paired with a cause test reading the accumulated time back through `run_time_for_test()`. `CupdlpWrapper.cpp`'s `getUserParamsFromOptions` computes a remaining-time adjustment and then assigns the *unadjusted* `options.time_limit` to `floatParam[D_TIME_LIM]`; a bump reviving that dead adjustment changes what the per-solve limit means and must re-derive this.
- Test hooks — `tolerances_for_test()` (reads `kkt_tolerance` back plus the three options that must **stay at their defaults**), `run_time_for_test()`, `presolve_status_for_test()` — take no lock and are **dispatching-thread-only, with no solve in flight**.

## Shared utilities (`src/`)

- `heuristic_common.h` — `HeuristicResult`, `CscMatrix`, row violation, clamping, effort-budget and patience sizing. Not the deadline: that is `ExecutionContext` in `heuristic_context.h`.
- `clique_cover` — the paper's Sect. 4.1 clique-cover constructions, as pure functions over a clique-table snapshot. `build_clique_cover` is the five-step greedy `typecl` uses and, by the paper's own sentence, `cliques` shares: equality cliques first (only ones disjoint from what is already in the cover, in clique-table order), then a largest-covering-clique assignment over the rest with one local-adjustment pass and a size-descending sort, members within a group in clique order, uncovered binaries appended in formulation order. `cliques2_order` is Fig. 3, a *different* cover — one pass over every clique, no partition step, driven by the zero-obj vertex — and it **skips an entire clique** whose literal is already fixed true. Both replace `HighsCliqueTable::cliquePartition`, which has no equality pass, no disjointness test, no size sort, and reorders within a clique; the paper's construction needs the table's equality flag and stored literal order, so the patch adds two const accessors (`getCliques()` / `getCliqueEntries()`). Being a table read, it is bound by the dispatching-thread rule.
  - **The per-clique vector allocations are hoisted and must stay that way**: `keyed` in `fpr_var_order.cpp` is declared outside the per-group loop and cleared inside it; `picked` / `selected` in `clique_cover.cpp` are function-scope.
  - **Two deliberate interpretations.** The Fig. 2 sampling key is the standard Efraimidis-Spirakis `log(Rand(0,1))/w_j` sorted descending, not the figure's `log(Rand(0,1)/w_j)` ascending — recorded as an ambiguity above `rank_cliques`; **do not "fix" that comment back into a claim about the figure.** The **size-sort direction** is the second: the paper names none, and descending is our reading.
  - There is deliberately **no minimum group size** — the paper's greedy has none, a threshold would be a deviation rather than a gap being filled, and an earlier `kMinCliqueGroupSize = 2` was measurably inert.
  - The path only **reads** the clique table where `cliquePartition` mutated it, so this is a net thread-safety improvement, and dropping the shuffle stops perturbing the table's RNG stream (an intentional behaviour change). Note `build_bare_mipsolver` turns HiGHS presolve off, which leaves the clique table **empty** (it is `HPresolve` that extracts cliques), so the tests drive a real `HighsCliqueTable` through the public `doAddClique`; no bundled instance yields an equality clique after presolve, so step 1 is synthetic-only coverage.
- `solution_pool` — thread-safe top-K solution pool with crossover restarts. It is a **restart reservoir, not an incumbent store**: HiGHS's `addIncumbent` takes a solution only when it strictly improves the upper bound, so the pool's looser admission never loosens what the solve reports. That looseness is `kDiversityObjTolerance` — a full pool also admits a solution within 10% of the best when it is at least `kDiversityMinHammingFrac` from *every* entry — and it exists so crossover has diverse parents. The diversity path evicts the admitted offer's nearest neighbour **other than the best entry, which it may never evict**: it runs only on an offer the pool already considers dominated, so evicting the best would degrade `copy_best` and the crossover's better parent until the pool refilled. Diversity is still measured against the best; only eviction skips it.

## HiGHS options added or touched by the patch

- `mip_heuristic_effort` — **vanilla semantics, vanilla default (0.05)**. This is upstream's B&B heuristic knob: `moreHeuristicsAllowed()` admits B&B-dive heuristics while `heuristic_lp_iterations < total_lp_iterations * mip_heuristic_effort` (plus an initial 10000-iteration offset). It gates RENS/RINS *and* `fpr_lp`: `fpr_lp::run` sizes each call to the remaining LP-iteration headroom of that envelope (converted at `nnz` effort-units per LP iteration, capped at `heuristic_effort_budget(nnz, mip_heuristic_effort)`) and charges all consumed work — reference-LP solves plus worker effort — back to `heuristic_lp_iterations`/`total_lp_iterations`, so fpr_lp competes with RENS/RINS for the same budget instead of drawing unaccounted work. **A patched binary at default options matches vanilla's B&B heuristic budget exactly.**
- `mip_heuristic_fj_effort` / `mip_heuristic_fpr_effort` / `mip_heuristic_local_mip_effort` / `mip_heuristic_scylla_effort` — one effort budget multiplier per **presolve** heuristic, each a double in `[0.0, 1e6]`; budget = `value * (nnz<<10)` — a multiple of vanilla HiGHS's own hardcoded single-thread FJ limit, so `effort = 1.0` means exactly one vanilla FJ budget and the patience option beside it is in the same unit. The ceiling of `1e6` exists so a calibration probe can hand a heuristic a budget that *cannot bind*, leaving the wall clock as the single stopping rule. Budget is derived in `run_sequential` from the model's `nnz`. They are **independent**: raising one heuristic's budget does not lower the others'.
  - **FJ's option sizes one worker's allowance**; the other three size a whole dispatch, which `make_budget` divides by N. The `budget_is_per_worker` flag in `kChain` is the only place that distinction lives (spelled out because `per_worker` in that translation unit already means `HeuristicBudget::per_worker`, a size_t budget rather than a flag).
  - Defaults are **measured**: fj `0.5665`, fpr `12.2559`, local_mip `13.9607`, scylla `3.068` — each the median budget that reached a dispatch's last incumbent improvement over the 233-instance PLATO list at 16 workers, taken over the dispatches that *finished* improving (a barren dispatch has no knee; a still-improving one is right-censored). `bench/ablation_effort/README.md` carries the derivation. `tests/test_smoke.cpp` pins all four, because they live in `apply_patch.cmake` where nothing else checks them. Treat them as the starting point of a calibration, not the result of one — and read the cross-build caveat under Patience before comparing them with a number measured on an older build.
  - Note: LocalMIP's reported effort folds in the cold-start construction sweep (Phase B greedy sweep from `local_mip_construction.cpp`, charged in coefficient-access units to match `WorkerCtx::effort`) on dispatches where pool and incumbent are both empty; the cheap Phase A column-write loop is excluded from the normal-path total for unit consistency, but a small `ncol` charge is still reported on the degenerate `nrow==0 || max_effort==0` early exit.
- `mip_heuristic_fpr_lp_effort` — the dive-time `fpr_lp`'s budget, a double in `[0.0, 1e6]`, default **`0.0`** — i.e. **`fpr_lp` ships off**. **Not in the unit of the four above**, and not a multiple of `nnz << 10`: `fpr_lp` draws from upstream's RENS/RINS LP-iteration envelope and charges back what it spends, so its budget is zero-sum against those two rather than an independent allowance, and the option is its **share of that envelope** (`fpr_lp::dive_budget`). `1.0` takes the whole slice. `fpr_lp` is the one heuristic of the five that has never been calibrated, and shipping an unmeasured heuristic whose budget is zero-sum against RENS/RINS is not neutral, so it stays off until #165 shows it earns that share. `0` disables the heuristic from the same return as the suite gate, above every counter read. One consequence for reproducing the recorded PLATO table: the config `fj+fpr+local_mip+fpr_lp` sets the token but not the effort, so that arm additionally needs `--extra-options mip_heuristic_fpr_lp_effort=1.0`.
- `mip_heuristic_suite` — **the** heuristic selector, default `all`. The value is either one of the two whole-value aliases `off` / `all`, or a **comma-separated list** of the heuristic names `fj`, `fpr`, `local_mip`, `scylla`, `fpr_lp`, so all thirty-one non-empty subsets are expressible. Order is irrelevant, whitespace around a token is trimmed, repeats are harmless. It gates `fpr_lp` too (via `heuristics::effective_flags`), so any value not naming `fpr_lp` disables the dive-time heuristic — **including `fpr`, which does not imply it**.
  - **`heuristics::effective_flags` in `src/mode_dispatch.cpp` is the single place the string becomes five booleans** — the dispatcher and `fpr_lp` both call it, and the four presolve names are `kChain`'s own `name` field rather than a second table, so a suite token cannot drift from the `[Heur] name=<n>` trace it produces. `fpr_lp` is the one token outside that table, because it is not a chain entry; `heuristics::kFprLpName` (`src/mode_dispatch.h`) is its single spelling and is what `fpr_lp.cpp` passes to `charge_dive`, which gives it the same property. That header is inserted into HiGHS's own `HighsMipSolver.cpp` and compiled at `CMAKE_CXX_STANDARD 11`, so the constant is a plain `constexpr char[]` — the same C++11 constraint `fpr_lp.h` is under.
  - `off` is an alias for the *whole* value and never a token in a list (`fj,off` is rejected): the patch compares `mip_heuristic_suite == "off"` verbatim in two places, so a value that selected nothing without being that exact string would run no heuristic at all — not even HiGHS's own FJ, which `off` deliberately keeps. `setLocalOptionValue` strips *spaces* — only spaces — from both ends of a string option's value and lower-cases it before storing (the options-file loader strips tabs, newlines and quotes first), which is what makes that exact comparison safe on both sides of the patch boundary: whatever neither strips misses `== "off"` identically in our parse and in the patched tree.
  - HiGHS does not validate the *value*, so an unknown one is accepted by `setOptionValue` and caught at solve time, where the dispatcher warns — **naming the offending token**, because one typo inside an otherwise valid list silently promotes the run to every heuristic — and fails open to all five. An empty value or a stray trailing comma is an unrecognised token, not a silent `off`.
  - **`off` is the "our four presolve heuristics disabled" ablation, and that is all it is. It is not a vanilla baseline and must never be used as one** — the baseline is always a separately built unpatched binary. `suite=off` restores HiGHS's own standalone FeasibilityJump call site, so `off` alone still runs FJ, but it is *our corrected copy*, not HiGHS's. `off` plus `mip_heuristic_run_feasibility_jump=false` is the nothing-at-all configuration, and it is the one `bench/check_vanilla_equivalence.py` compares against an unpatched binary. `tests/test_native_fj.cpp` pins what `off` does promise: the native call site runs and charges `heuristic_effort_used`, and stops doing both when `mip_heuristic_run_feasibility_jump=false`.
- `mip_heuristic_presolve_only` — bool, default `false`. After the presolve chain completes, exit the solve **before the root LP**, keeping the incumbent. Reports `HighsModelStatus::kSolutionLimit`, which is what HiGHS itself assigns for a user-configured search-size limit and — unlike `kNotset`/`kInfeasible` — is *not* rewritten by `cleanupSolve`, which would otherwise stamp `kOptimal` on a solve that never computed a dual bound. So a presolve-only run reports `Dual bound -inf`, `Gap inf`, `Nodes 0`, `LP iterations 0`, CLI exit **1** (`HighsStatus::kWarning`), and a finite `Primal bound` with real incumbent display rows when the chain produced something. `run_benchmark.py` accepts exit 1, so these land in a normal `.log`. It is ~25x cheaper than a full solve and the only way to measure the chain without B&B diluting it.
- `mip_heuristic_fj_patience` / `mip_heuristic_fpr_patience` / `mip_heuristic_local_mip_patience` / `mip_heuristic_scylla_patience` — **a double in the same unit as that heuristic's effort option**, defaults 0.1416 / 3.064 / 3.4902 / 0.767 — measured, each the p95 wait for the next incumbent improvement clamped to a quarter of that heuristic's ceiling, which is why every one of them is `0.25 x effort` to rounding (both columns ship at four decimal places, the precision the measurement supports). See the patience section below for scope and for what `0` means.
- `mip_heuristic_run_feasibility_jump` — upstream's own FJ switch, and the one pre-existing option the patch still reads. `false` disables FeasibilityJump at every suite value: at `off` it gates HiGHS's native call site, elsewhere it gates ours. `suite=off` plus this set to false is the pure patch-overhead configuration.

## Patience: absolute, and read off incumbent improvements

Every presolve heuristic stops early when improvement-free effort crosses a threshold, at two levels — a runner-level gate over the whole dispatch (`ContinuousLoopState::effort_since_improvement` against `HeuristicBudget::stale`) and a worker-level gate in `WorkerBudgetState`.

**The threshold is an option, not a fraction of the budget.** `mip_heuristic_<name>_patience`, read through `kChain`. A threshold derived from the budget cannot bound over-budgeting: doubling the budget doubles the tolerance, so the gate never fires relatively sooner. The four are **not comparable across heuristics**, because only each heuristic knows what its own effort counter counts. **`0` means no gate at all** — unbounded, returned ahead of the clamp — not "give up immediately"; that is what lets a probe measure a heuristic with nothing stopping it.

`patience_threshold(nnz, per_base, budget)` in `heuristic_common.h` applies one, **clamped to `budget / kPatienceCeilingDivisor`, a quarter, not to `budget`**: a patience at or above the ceiling fires exactly at exhaustion, which is behaviourally identical to no gate and reported nowhere — and that is the *common* case for an honestly measured value, since the measured p95 exceeds the ceiling on three of the four heuristics. A quarter is FJ's own shape and is exactly where all four shipped defaults sit. `run_sequential` sizes the runner-level gate (multiplying by the worker count for FJ, whose option's scope is per-worker like its effort option) and `make_budget` divides it by N into `worker_stale`. **Scylla is the one documented deviation**: it takes the dispatch-level `stale` as its worker threshold, because its per-worker counter is charged the PDLP cost already divided by N.

**The improvement signal is an incumbent improvement, not a pool acceptance.** The pool keeps a top-K, so a heuristic that merely beats its own worst entry would reset staleness forever — measured over 233 instances at 16 workers, FPR earns ~3.3M pool acceptances against 590 incumbent improvements, and a patience calibrated on improvements cannot be spent against a gate that resets on acceptances. So `offer` returns **two** facts (`IncumbentSink::OfferResult{accepted, improved_incumbent}`, `[[nodiscard]]`): gates read `improved_incumbent`, decided inside `SolutionPool`'s own lock against the best objective the pool has ever accepted — the only race-free place, since a worker may not read a solver field — and a **monotone watermark** rather than `entries_.front()`, which the diversity-replacement path can evict, degrading the pool's best where the solve's never degrades. `accepted()`, `[Heur] found` and `[HeurSol] accepted` keep their pool-acceptance meaning, because `bench/parse_highs_log.py` and external tooling depend on it. **Returning a struct rather than repurposing the bool is deliberate**: it makes every gate site name which fact it reads.

**`CMakeLists.txt` puts `-Werror=unused-result` on `mip_heuristics` and `mip_heuristics_tests`**, without which a re-drop of that result is only a warning — nothing here passes `-Werror` and the clang-tidy gate cannot see `clang-diagnostic-*`, since `.clang-tidy` opens with `-*`. Keep that flag on our two targets and off HiGHS's. The two deliberate discards (`fpr_lp`, LocalMIP's cold-start publish) are spelled `static_cast<void>` with a reason.

**Only the gate's operand is the incumbent notion** — LocalMIP's `best_objective_`/`steps_since_improvement_` and FJ's internal `effortSinceLastImprovement` are the local search's own bookkeeping and still use the local notion.

**Scylla has a granularity floor no constant can cross**: one attempt charges a whole PDLP solve (`iters x nnz`), several times the ceiling, and `attempt_cap` does not govern a solve once started. Do **not** try to fix that by clamping `attempt_cap` — measurably ineffective.

**Caveat when comparing effort numbers across builds.** The four effort defaults and both patience columns are quantiles on *charged effort* and on *incumbent improvements*. Landed changes have moved how much effort a unit of real work charges (the in-tree repair's per-refuted-node scan, on FPR / Scylla / `fpr_lp` alike; the uncapped Phase 3; the epsilon route's cheaper pump iteration; `presolve=off` on the shared PDLP instance) and how a heuristic searches at all (FJ's two corrections, RepairSearch's jump and disjunction, the pump advancing on a failed rounding). **Any number quoted from a run older than the code in front of you is on a different axis** — re-measure rather than reconcile.

## The wall-clock deadline

**The deadline is bounded by a polling interval, not by an attempt.** `ExecutionContext` exposes two predicates, and which one a caller may use is a thread-safety fact, not a preference:

- **`past_deadline()`** is `timer_.read() >= time_limit` alone. `HighsTimer::read()` is `const` and writes nothing for the solve clock, so **any worker thread may call it** — that is what lets every heuristic poll the deadline from inside its own inner loop.
- **`terminated()`** adds `terminatorTerminated()`, which *writes* `mipsolver.termination_status_` when a terminator is attached, and is therefore **seat-holder-only** via `ContinuousLoopState`. `run_sequential` also calls it between heuristics, where every parallel region has joined. **There is no exception to this rule.**

Cadences: FJ per upstream callback (`CALLBACK_EFFORT` = 500000 effort units); LocalMIP every `kTermCheckWork` counted units of `WorkerCtx::effort` — **work, not steps**, because a feasible-mode step calls `WorkerCtx::full_recheck` every `kFeasibleRecheckPeriod` steps and that charges one `nnz`, so the wall time a fixed step count buys scales with the model; FPR per inner attempt, every `kDeadlinePollNodes` DFS nodes, every RepairSearch node, every `repair_walk` step, *and* every `kPropagateDeadlinePollWork` counted units inside a propagation fixpoint; Scylla per pump iteration. The runner polls unconditionally on every iteration too (`ContinuousLoopState::should_stop`), which stops a worker that ended its attempt *on* the deadline from spinning on empty attempts.

`Deadline` (`src/deadline.h`) is the poll in the form a *sub-algorithm* takes it — a `const HighsTimer*` and a limit, null when the limit is infinite — for the layers below a runner that have no `ExecutionContext` (`fpr_core` is reached from `FprWorker`, `ScyllaWorker` and `fpr_lp`). **`ExecutionContext::deadline()` and `deadline_of(mipsolver)` are the only two ways to build one**, so a sub-algorithm cannot stop against a different clock or limit than its runner. Two callers need the *scalar* remaining time to hand a sub-solver rather than the predicate, and both read it off a `Deadline`: `ContestedPdlp` inside its mutex, and `fpr_lp`'s reference LP solves through `Deadline::remaining()`. **Don't inline `time_limit - timer_.read()` as a second spelling** — the same clock read in a file whose caller then cannot tell an expiry from a failed solve.

**The sequential dispatch setup is deadline-gated too**, and its cost is independent of every option: `fpr::precompute_var_orders` (8 orders), `ContestedPdlp` construction plus `scylla::precompute_config_var_orders` (5 orders), and `fpr_lp`'s `build_setup` (10 orders + 2 reference LP solves) all run before any worker exists and can each take tens of seconds on a large model. Each checks the deadline between orders and returns with an incomplete table rather than finishing the list, reporting `abandoned_setup=1`.

Two things this does **not** do: it does not un-truncate the chain — a heuristic that legitimately spends the whole limit still leaves its successors nothing, since `run_sequential` skips a heuristic once `exec.terminated()` — and it does not remove Scylla's floor of one whole PDLP solve. It also narrows reproducibility: a run whose deadline binds is wall-clock dependent even at `threads=1`, so a high-effort measurement run needs a limit its chain does not reach.

**Residual floors** (all in `docs/PARAMETERS.md`, "What bounds the deadline's tightness"): one LocalMIP local-search step plus `kTermCheckWork` counted units; `kPropagateDeadlinePollWork` counted units plus one row inside a propagation fixpoint; one `repair_walk` step — O(row degree x column degree) plus an O(`nrow`) rescan on a soft restart, which on a model with a dense row exceeds a propagation poll and makes it FPR's coarsest unit; one `compute_var_order`, the largest of them, scaling with the model into seconds on a large instance; one PDLP solve including the wrapped `Highs::run`'s own LP setup, plus `ContestedPdlp`'s own LP build, which is ahead of the first deadline check; and FJ's worker construction.

## Observability

At `log_dev_level=3` `EffortLedger::book` (`src/effort_ledger.cpp`) emits one line per presolve-chain heuristic per solve, plus one per `fpr_lp` dive dispatch. `bench/parse_highs_log.py` parses all of them.

- `[Sequential] heur=<name> effort=<N> wall_ms=<X> effort_per_ms=<R>` — **positional**, because external tooling reads it. Keep it alongside `[Heur]`.
- `[Heur] name=<n> phase=<presolve|dive> start_s=<S> end_s=<E> effort=<N> wall_ms=<X> effort_per_ms=<R> found=<0|1> nnz=<Z> abandoned_setup=<0|1>` — **key=value**, same emission site. It carries what `[Sequential]` cannot: *when* the heuristic ran on the solver clock, which side of the patch boundary it ran on, whether it produced anything, and whether it ran at all. This is the line a per-heuristic budget calibration reads.
  - `nnz` comes from `mipdata->ARindex_.size()` — the post-presolve MIP matrix the effort and patience options are denominated in. It exists because **`log_dev_level=3` suppresses the model header a parser would otherwise read**: the one-line `MIP <name> has ... nonzeros;` form is absent from every level-3 log. The level-3 `Rows/Cols/Nonzeros` block is *not* a substitute — it is the pre-presolve model.
  - `abandoned_setup` distinguishes a heuristic that searched and produced nothing from one that **never searched**. **Three log shapes must stay distinguishable**: no `[Heur]` line at all is a killed run, `abandoned_setup=1` is a setup bail, and the field absent or `0` is a dispatch that ran. It is emitted unconditionally on **both** the `charge_presolve` and `charge_dive` paths, so an *absent* field means one thing only — a log written before the field existed — and `HeuristicSample.abandoned_setup` is `None` there rather than `False`, since the distinction is unobservable on such a log rather than known-absent.
  - **There are two channels from a bail site to the ledger, and which one a heuristic uses follows from whether it books itself.** The four presolve heuristics are on the shared runner contract, so theirs is its return type — `DispatchOutcome` (effort + flag) in `heuristic_context.h`, booked by `run_sequential`. `fpr_lp` books its own dispatch, so its bail reaches the line as an explicit `charge_dive` argument and by nothing else. **That argument is deliberately not defaulted**, so a future dive-shaped caller cannot inherit `false` without considering the question.
  - **Never infer the bail from `effort == 0` plus an expired deadline**, in a log or in process: a dispatch entered with a millisecond left constructs its workers and exits at zero effort without ever bailing in setup. Only the bail site knows, which is why the flag is returned rather than reconstructed.
- `[HeurSol] name=<n> dispatch=<i> worker=<w> effort_at=<E> wall_ms=<X> obj=<O> accepted=<0|1>` — **key=value**, one per **accepted** `IncumbentSink::offer`, at `log_dev_level=3` only. It gives the intra-dispatch view `[Heur]` cannot: productive effort (charged effort at the last accepted offer), stale effort, and the inter-acceptance gap distribution that calibrates a patience. It is narrowed to acceptances because the raw offer rate reaches ~11k/s on a small model — tens of MB per run for lines no consumer reads. The `accepted` field stays in the format (the parser requires it, and older logs carry both values); anything wanting a raw offer rate wants a counter in `[Heur]`, not a line per offer.
  - `dispatch` is a **process-global** counter — unique per dispatch, never dense or zero-based per solve — so group on `(name, dispatch)` and bind to the closing `[Heur]` line via `HeurSolSample.heur_index`, which is **the supported binding**; re-deriving it is how three of four heuristics silently vanish. `effort_at` is monotone only within a `(name, dispatch, worker)` triple, and is that heuristic's own unit.
- The ledger times against HiGHS's own solver clock, so `[Heur]` windows share an origin with HiGHS's display-line time column. That clock is **not** monotonic — `HighsTimer` bottoms out in `high_resolution_clock`, which libstdc++ aliases to `system_clock` — so a wall-clock step can produce a negative `wall_ms`. The bench regex accepts the sign so such a sample surfaces instead of silently vanishing.

**`effort_per_ms` measures *charged* effort, not useful work**, so it is **not a valid before/after metric** for a change that alters how much effort a unit of real work charges — only for comparing heuristics against each other at fixed code. Removing redundant work usually *lowers* it: an incremental-structures build can report a 2.8x rate loss on a 10x throughput gain, because the naive path charged a full `nnz` recheck it did not need. **Measure real work units** (LocalMIP steps, FPR DFS nodes per ms) when A/B-ing a hot-path change. Keep the four presolve heuristics and `fpr_lp` apart when comparing rates: they draw from different budgets. `effort_per_ms` is also a throughput, and Scylla scales sublinearly in workers (PDLP mutex) where FPR/LocalMIP scale near-linearly, so the worker-count factor does not cancel in cross-heuristic ratios — state the worker count with any such ratio.

**The presolve chain is ~4% of a solve, and that number is what retires a performance issue.** At shipped defaults the whole four-heuristic chain costs ~1.07 s on `50v-10` and ~1.73 s on `roll3000`, against a 43.6 s optimal solve of the latter — ~0.25% at a 600 s campaign limit — and it is *budget*-bound there rather than clock-bound, so a faster implementation does not search more, it hands the difference back to B&B. One FPR presolve dispatch is ~98 ms. Two hotspots larger than anything on the retired perf list are deliberately unfixed, recorded so the next profile does not re-derive them: ~31% of an FPR dispatch is `SolutionPool`'s diversity scan (`hamming_distance` plus a `std::round` per column, against every pool entry on every offer) and ~15% is `clock_gettime` from deadline polling — ~30 ms of a 43 s solve between them. (Shares from a sampling profiler at 500 Hz, `perf` being blocked by `perf_event_paranoid` here; read them to one significant figure.) **Before filing or accepting the next micro-optimization, price it against the 4%**: the bar is not "is this redundant work" but "is this worth more than the re-baseline and the verification it forces".

## Benchmarking

`bench/` has scripts for MIPLIB benchmarks — `run_benchmark.py` runs instances, `analyze_results.py` parses results.

**Where MIPLIB lives.** The collection is **not** at a fixed path: `bench/download_miplib.sh` and `run_benchmark.py --data-dir` share a search path — explicit argument, then `$MIPLIB_DIR`, then `~/data/miplib`, then `/tmp/miplib` — and the first directory holding more than 200 `.mps.gz` files wins. It is 3.5 GB, so it lives once per machine outside every checkout; `/tmp` is probed (an existing copy is reused) but never written to, since it does not survive a reboot. **That search path and its >200 threshold are defined twice, once in bash and once in Python**, and drift between them is silent and expensive — the downloader writes one directory while the benchmark reads another. Three tests in `bench/test_run_benchmark.py` parse the shell script and assert both against the Python constants; keep them passing rather than editing one side alone.

**Don't pass `--threads`** (or set `threads=` in an `.opts` file) unless asked — let HiGHS use its default; forcing `threads=1` collapses each heuristic to a single worker (the right setting for reproducibility, the wrong one for a throughput benchmark).

**The vanilla baseline is always a separately built unpatched binary** (`--vanilla-binary`, matching tag). Two binaries is the design, not a preference or a fallback, and `run_benchmark.py` enforces it:
- `vanilla` is not a `CONFIG_SUITES` entry — it names a binary, not a suite value, and carries no options. `build_plan` raises when the config is asked for without `--vanilla-binary`.
- `check_vanilla_binary` runs the named binary **with no arguments** before the first solve, refusing it if the banner carries `mip-heuristics patch active` or reports a version other than the `GIT_TAG` in `cmake/FetchHiGHS.cmake`. **The no-argument invocation is the whole trick**: `--version` never reaches `highsLogHeader`, so it prints neither the marker nor the `Running HiGHS <v> (git hash: <h>)` form, and a probe there would silently pass a patched binary. Only the *version* decides anything in that banner; the git hash is captured for a manifest and compared by nothing, which is why `BANNER_RE` accepts `[^)]+` there — HiGHS sets `GITHASH` to the literal `n/a` when configured outside a git repository, so a distro package would otherwise be refused for "printing no HiGHS banner" in a message quoting that banner.
- The probe is **symmetric**: `--binary` must carry the marker and match the tag, because a stock HiGHS there has none of the options the configs set and every run would exit 255. Each binary is probed only if a plan uses it, so `--configs vanilla` alone never touches the patched build.
- `check_known_options` is the second half of the pre-flight and runs against **every distinct binary the run will use**: HiGHS exits 255 without solving on an unknown option name, and `--extra-options` applies to every config, so one bad key fails every instance of every config on that binary and leaves a resume loop relaunching a campaign that cannot advance. It asks the binary one key at a time (HiGHS stops reading an options file at the first unknown key, so one probing run names one offender) rather than filtering on a `mip_heuristic_` prefix: of the seventeen `mip_heuristic_*` names a patched build carries, **seven are upstream's own** and legal on both binaries — `mip_heuristic_effort` plus the six `mip_heuristic_run_*` switches (`feasibility_jump`, `rens`, `rins`, `root_reduced_cost`, `shifting`, `zi_round`) — so a prefix rule would refuse a valid sweep and a hardcoded list of the other ten would need editing on every option change.
- `run_plato.sh` has **no default for the vanilla binary at all** — no fallback to `$BINARY`, no `command -v highs` PATH search: a baseline whose binary was discovered rather than named is a baseline nobody chose. The empty `--vanilla-binary` it may pass is read as "not given", the same convention `--data-dir` uses.
- `bench/check_vanilla_equivalence.py` compares the configuration where **both sides disable FeasibilityJump** (`suite=off` plus `mip_heuristic_run_feasibility_jump=false` against upstream's own switch), which is the part worth proving: that injecting the heuristics moves neither presolve, nor B&B, nor the LP path. What that narrowing no longer covers is pinned by `tests/test_native_fj.cpp` instead.

**Killed runs are kept, not discarded.** HiGHS checks its clock between work units, so one long simplex solve at the root can pass `time_limit` without returning to look. `run_benchmark.py` keeps the partial stdout and appends a `TIMEOUT: process killed after Ns` marker, which `parse_highs_log.py` turns into `killed` and a `Killed (timeout)` status, and `analyze_results.py` lists under "Killed runs". Those logs still score correctly — T1st and the primal integral read the incumbent lines, never the Solving report the run never reached — and are deliberately *not* retried on resume, since rerunning reproduces the same hang. Only a kill before the binary printed anything becomes a `.log.err`, which is the shape that does get retried.

Patched binaries self-identify with a `mip-heuristics patch active` line right after the version banner (injected by `apply_patch.cmake`) — the version/githash banner alone is identical between patched and unpatched builds of the same tag (at equal clone depth; see the `GIT_SHALLOW` note in Build Commands).

`run_benchmark.py` leaves `log_dev_level=3` off behind `--dev-log`: level 3 and the headline timing are not the same run.

### Configs

`run_benchmark.py`'s config surface is exactly one entry of `CONFIG_SUITES` per `mip_heuristic_suite` value, with no aliases, plus the one name that is *not* a suite value: `vanilla`. `KNOWN_CONFIGS` is the union, and `resolve_config` raises against it.

Subset names use **`+` where the suite value uses `,`** (`fj+fpr` → `fj,fpr`): a comma is legal in a directory name but not free in a generated table or in LaTeX. Subset names list heuristics in selection order — the presolve chain in dispatch order, then `fpr_lp` — so one subset has exactly one spelling (`fpr+fj` is not a config, and neither is `fpr_lp+fj`). The thirty-one subsets are **generated** from the ordered name tuple `SUITE_ORDER` rather than written out, so the chain-order spelling and the name-is-the-suite-value-with-`+` property hold by construction. The full five-element subset is spelled `all`, its long-standing alias, so it appears once.

**`config_options` raises on an unknown config name** — it used to return `{}`, so `--configs patchd` produced a fully populated, plausible-looking, completely meaningless results tree. A config name carries **no budget of its own**: every heuristic runs at its shipped default, and moving one for a run goes through `--extra-options`. `build_plan` is the single place a name's two consequences — which binary, which options — are chosen together; choosing them at separate use sites is how a name picks one branch's binary and the other branch's options. A run that solved but ignored its configuration is routed to `<inst>.log.err` like a non-solving exit, because HiGHS accepts an unknown `mip_heuristic_suite` value and `run_presolve` fails open to every heuristic with a warning and exit 0.

### Tuning subsets

`bench/make_tuning_set.py <vanilla-results-tree> --instances bench/instances_plato.txt --size N --seed S` derives a stratified tuning list and prints the stratum table to stderr (the list goes to `--output`, stdout by default).

It stratifies on **vanilla time-to-first-feasible** — read through `parse_highs_log`, not a second parser — because that is the axis the PLATO primal integral responds to. `bench/instances_small.txt` is stratified on *optimality* solve time and stays exactly as it is, being the recorded input of earlier budget work and the set per-heuristic budget work runs on.

Strata are half-open intervals split at `--boundaries` (default `1,10,100,600`) plus a `never` bucket and a `>=600s` overflow bucket — **a solution found at or past the time limit is hard, not never-feasible**, and must not be filed as one. Allocation is largest-remainder proportional in *integer* arithmetic, with `--min-per-stratum` seats reserved off the top so a 3-of-233 stratum is not rounded out of the set it was stratified for. **The integer arithmetic is load-bearing**: where the integer remainders are a mathematical tie, float shares carry fractional noise that sorts them into a different order and hands the seat to the wrong stratum — an observed test failure, not a hypothetical. No cap is applied on top: `alloc <= population` follows from `rest <= room_total`, and a sweep in `bench/test_make_tuning_set.py` checks it rather than the code clamping something that cannot bind.

The emitted header records source tree, config, seeds, boundaries, allocation rule and both distributions, and deliberately carries **no timestamp**: same tree plus same `--seed` must be byte-identical. It refuses (exit 2) any tree not covering the reference list for every seed of the config, and two log shapes that would otherwise be binned as never-feasible: a *truncated* log (no solving report), and one reporting a finite primal bound with no incumbent line — which is what a source code missing from `parse_highs_log._INCUMBENT_SOURCES` looks like, i.e. what a HiGHS bump produces. `parse_highs_log` already `warnings.warn`s on that second condition; `unusable_reason` mirrors it so the diagnosis becomes a refusal instead of a mis-binned instance in the smallest stratum. `--allow-incomplete-seeds` is the one documented escape, and it is recorded in the header.

### Instance filtering, the config oracle, and reference data

`--instances FILE` restricts any report to an instance list and `--exclude-instances FILE` removes one, applied in that order to the *raw* tree before aggregation — which is why every table reports the count it covers without knowing a filter ran, and why the held-out complement is `--instances plato --exclude-instances tuning` rather than a third file that drifts.

`--oracle A B C` adds a best-of-those-configs row (`--oracle-name` renames it on collision, ≥2 participants required): selection is per instance on primal integral at `--time-limit`, **among exactly the seed-collapsed rows the tables already show**, which is what makes the row a true ceiling (headline SGM ≤ every participant's, instance by instance). **Do not "fix" this into per-`(instance, seed)` selection followed by `aggregate_results`**: that collapses picks chosen on primal integral by *median primal bound*, mixing two criteria, and the row can then score worse than a participant while still being labelled a ceiling (~2% of random two-seed trees). The oracle is additive and is held out of `#Win`/`#First` via the `synthetic` set. Instances absent from any participant at any shared seed, or outside the tables' common set, are dropped with the count reported — scoring an out-of-common instance is how selection goes wrong, since `best_known` is built over that set and a missing reference sends `primal_integral` to the dual bound and the tie-break to whoever is named first.

**"Virtual best" in that script is not the oracle** — it is `resolve_reference`'s handling of an observed primal that beats the published `.solu` value, and the module docstring says so; do not merge the two names.

Reference objectives live in `bench/miplib2017-v36.solu`, a verbatim upstream copy. An instance tagged `=inf=`/`=unbd=` is excluded from every table with the exclusion printed, because the gap would otherwise fall back to the best observed primal and enter the SGM as a self-referential zero.

### Release archive

`bench/make_archive.py build <results-tree> --output <dir> --time-limit T` packages a results tree — logs, the `<instance>.opts` each run was given, generated tables, `MANIFEST.json` + `PROVENANCE.md` — and `verify` (wrapped by the archive's own `REGENERATE.sh`) re-derives every table from the archived logs and diffs it, so "regenerable from the archive alone" is checked rather than claimed.

The provenance is *derived*, not asserted: which binary produced a config comes from the `mip-heuristics patch active` marker in each log, since patched and unpatched builds of the same tag have identical version/githash banners. There is exactly one baseline claim — "separately built unpatched binary"; a baseline config whose logs carry the marker is recorded as "ablation on the patched binary — not a vanilla baseline". Instrumentation is recorded both as requested (`log_dev_level` in the `.opts`) and as observed (`[Heur]`/`[Sequential]` tags), because a disagreement is the `--extra-options log_dev_level=1` failure.

`--time-limit` is required because HiGHS takes it on the command line, so it is in no `.opts`. The effective worker count is recorded the same derived way: the harness deliberately does not pin `threads`, so the count appears in no `.opts` and is read from each log's `Thread count N (of M threads)` line into `run.workers_observed` (`parse_highs_log` exposes the same three numbers as `thread_count` / `hardware_threads` / `max_workers` — `thread_count` is HiGHS's pool size and therefore `ExecutionContext::num_workers`, `max_workers` is B&B's own cap, and they are different numbers). **Two distinct values across a tree means it mixes machines and its runs are not comparable**, which warns; neither pinned nor observed warns too. The machine block itself is auto-detected on the *archive* host — hence `--machine-note`.

A campaign yields two archives, headline-timing and `--dev-log` attribution; they are different runs. `docs/RELEASE.md` is the process around it, including the ordering constraint that Zenodo's GitHub integration must be enabled **before** the release is created (it does not backfill) and that `.zenodo.json` makes Zenodo ignore `CITATION.cff` entirely.
