# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Navigation: LSP → narrow Grep → sliced Read.

# Standards

## Communication Style

Be terse. No preamble. No filler.

## Code Navigation

Prefer narrow queries over full-file reads:

1. **LSP** for symbol questions — `goToDefinition`, `hover`, `documentSymbol`, `workspaceSymbol`. Use before `Read`.
2. **Grep** with `-n` and a small `head_limit` (start at 20); raise only if inconclusive.
3. **Read** with `offset`/`limit` for a slice around the hit. Full-file `Read` is fine under ~200 lines or when structure matters.

Know the symbol → LSP. Know a string, not its location → Grep. Full-file Read is the last mile. This is a preference, not a prohibition: shelling out to `grep`/`rg` is fine when the built-in can't do the job (filtering a pipe like `git log | grep`, or a session without the `Grep` tool). What matters is bounding output, not which binary produces it.

Setup: install `clangd-lsp@claude-plugins-official` plus `clangd` (`apt install clangd`, or from LLVM). `.clangd` points at `build/compile_commands.json`, produced by `CMAKE_EXPORT_COMPILE_COMMANDS ON`.

## C++

- Target C++23. Use modern features (`std::expected`, concepts, ranges, `constexpr`).
- Use `#pragma once`. Minimize header includes; forward-declare where possible.
- **Formatting** is Google, via `.clang-format`. **Naming is not Google** — `.clang-tidy` enforces what this codebase actually does:

  | Kind | Style | Example |
  |---|---|---|
  | Functions (free and member) | `lower_case` | `run_sequential`, `charge_presolve` |
  | Locals, parameters, `const` locals | `lower_case` | `per_worker`, `max_effort` |
  | Private members | **trailing** `_` | `FjWorker::start_`, `seed_` |
  | File-scope / static / class / `constexpr` constants | `k` + `CamelCase` | `kMaxStaleRounds`, `kNumLpArms` |
  | Classes | `CamelCase` | `ScyllaWorker`, `EffortLedger` |
  | Namespaces | `lower_case` | `heuristics`, `fpr` |
  | Files | `snake_case.h` / `.cpp` | |

  `ConstantMemberCase` is deliberately unset: it outranks `PrivateMemberSuffix`, so setting it would reject a `const` private member spelled with this project's `_` suffix. The `.clang-tidy` comments carry the reasoning for each narrowing — read them before changing one.

## Complexity

When a complexity warning fires, don't extract methods mechanically. Ask what the independent responsibilities are and split along those boundaries. If the function is genuinely complex because the domain is, add a comment explaining why and suppress the warning.

## CMake

- `set(CMAKE_EXPORT_COMPILE_COMMANDS ON)` for clang-tidy.
- Use FetchContent for dependencies.
- A single root `CMakeLists.txt`; per-directory files would only add indirection.

## Testing (Catch2 v3)

- `TEST_CASE("name", "[tag]")` with `[tag]` filters, in `tests/`. Not GoogleTest.
- Instances come from HiGHS's own `check/instances/` (path injected as the `INSTANCES_DIR` compile definition).
- `ctest --progress` collapses the running list and `CMAKE_INSTALL_MESSAGE=LAZY` suppresses install chatter. Don't remove these.
- **`[serial]` is a reserved tag** (#146), and it is the *last* resort for a timing-dependent test, not the first. `CMakeLists.txt` registers the tagged cases through their own `catch_discover_tests` call carrying `TEST_SPEC "[serial]"` and `PROPERTIES RUN_SERIAL TRUE`, beside a second call taking `TEST_SPEC "~[serial]"` for everything else; the two specs partition the suite exactly (verify with `ctest -N | wc -l` and a `uniq -d` over the names). Give each call its own `TEST_LIST` name — hygiene, not a live bug: `Catch.cmake` keys its generated include scripts on a SHA1 of `TEST_SPEC`, so they do not actually collide, and nothing here reads the variable. Order of preference when a test flakes under `ctest -j$(nproc)`: **(1) take the clock out of the fixture** — `tests/test_deadline.cpp` failed at `readModel` because HiGHS's free-format MPS reader takes `time_limit` as its own *parse* budget (`HMpsFF::start_time` runs from parse start; `gesa2` parses in 4-5 ms against a 0.1 s limit, a margin saturation closes), fixed by writing the option after the read, as `build_bare_mipsolver` in `tests/test_common.h` already did; **(2) assert the mechanism** — a starved runner spends *less* effort, so `effort < attempt_cap` only gets easier under load, which is why `tests/test_setup_bail.cpp` and `tests/test_patience_gate.cpp` need nothing here; **(3) only then tag it**, for a wait nothing in the code can bound (a 0.1 s solver limit a descheduled thread spends doing nothing, after which `run_sequential` skips the heuristic and emits no `[Heur]` line). **Never widen the constant** — a threshold tuned until it stops failing is the same test with a longer fuse, and here it would not even have worked. `RUN_SERIAL`, not `RESOURCE_LOCK`: these need an unloaded machine, not mutual exclusion. Neither excludes load from *outside* ctest, which is why (1) and (2) beat (3) whenever they are available.

## Development Workflow

```
plan (non-trivial) → implement → test → push to main
```

Nothing formats on save — there are no Claude Code hooks. `clang-format` runs at commit time: `pre-commit` formats the staged C++, applies safe `clang-tidy` fixes, and re-stages the result, so what you commit is canonical even though the file you just edited is not. Don't hand-tune formatting — let the hook normalize it, or run it yourself:

```
.venv/bin/clang-format -i <files>                       # normalize in place
.venv/bin/clang-format --dry-run --Werror <files>       # check only, non-zero if unformatted
```

**Use the venv's clang tools, not PATH.** The pinned 22.1.8 pair lives in `.venv/bin`, which is the exact path `cmake/Lint.cmake` searches; a different major version formats differently and fails the `clang_format` ctest gate. The hooks resolve the venv first for the same reason.

The hooks are **tracked in `.githooks/`** (`commit-msg`, `pre-commit`, `pre-push`, and the sourced `resolve-venv.sh`) — edit them there, not in `.git/hooks/`, which is empty of ours. Git only runs them when `core.hooksPath` points at that directory, and that setting is per-checkout config which cannot be tracked; `cmake -B build` sets it (option `MIP_HEURISTICS_INSTALL_GIT_HOOKS`, ON), leaving an existing `.githooks` value alone and warning rather than clobbering a hooksPath someone else set. To wire a clone up by hand: `git config core.hooksPath .githooks`. `.claude/` is gitignored, owned by this repo, and not part of the published artifact — edit it in place; it holds only permission rules and a statusline. A new Claude Code hook must read its file path and command from the hook JSON **on stdin**, never `$CLAUDE_FILE_PATH` (unset by Claude Code — a hook reading it no-ops silently rather than failing; the formatter this project inherited did exactly that). The clang-format and clang-tidy gates deliberately live outside the hooks, as ctest tests labelled `lint` plus the CI job, so a fresh clone still runs them. **Never `git push --no-verify` or `git commit --no-verify`** unless asked; a failing hook is a signal, so fix the root cause.

## Git Workflow

Trunk-based, linear history on main. Commit directly to main and push when local gates pass.

Feature branches are optional for larger changes: always branch from main (`git checkout main && git pull` first), never from another feature branch, keep them short-lived, and rebase or squash merge — no merge commits on main.

After a successful push:
- **Close any gh issue the work resolved**: `gh issue close <num> -c "<one-line note>"`, for every issue the push covers.
- **Delete the feature branch** if one was used: `git branch -d <branch>`, plus `git push origin --delete <branch>` if pushed.

## Commit Messages

Conventional Commits; the commit-msg hook enforces format.

- `type: description` or `type(scope): description`
- Types: `feat`, `fix`, `refactor`, `test`, `docs`, `style`, `perf`, `chore`, `build`, `ci`
- Subject ≤72 chars. Focus on **why**, not what.

## Issue Tracking

GitHub Issues, via the `gh` CLI.

- **Default to HTTPS** for GitHub remotes, not SSH.
- **Read an issue** with `gh issue view <num> --json title,body,labels,state,comments`; plain `gh issue view <num>` is deprecated for programmatic use.
- Don't defer work into a new issue unless it is substantial. Fix small follow-ups inline or leave them alone.

Issues get picked up cold, in fresh sessions, often by an agent with no access to this machine. So: keep the body **self-contained** (problem, motivation, acceptance criteria, repro steps); use **no local references** (`/home/user/...`, "see my other checkout" — dead links in a fresh session); prefer **stable external links** (GitHub permalinks, papers, RFCs); and **describe local code by concept, not path**, hinting that the agent can search under `..`, `../..`, or `~/code/`.

## Working Rules

- **CLAUDE.md discipline.** When Claude gets something wrong, fix CLAUDE.md in the same commit. It's a living document — update it whenever better instructions would have prevented the mistake.
- **Follow the agreed plan.** If a plan should change, stop and discuss — don't silently diverge. Same outside a written plan: if the current approach isn't working, say so rather than quietly switching strategies. Implement everything specified; no TODO placeholders or stubs unless asked.
- **Match references exactly.** Implementing from papers, pseudocode, or open source: no early exits, iteration limits, size caps, or "optimization" shortcuts that change behaviour. Introduce heuristic approximations only when asked. Implement the edge cases rather than simplifying them away. When in doubt, be faithful and let tests verify.
- **Don't invent APIs.** Verify functions, flags, and methods exist before using them.
- **Don't ignore type errors.** If clang-tidy or ruff flags something, fix the root cause — don't suppress.
- **Don't use deprecated patterns.** Check current docs, not training data.
- **Performance matters.** Most of this is solvers: profile before micro-optimizing, but don't sacrifice perf for "clean code".

# Project: mip-heuristics

## Project Overview

Custom MIP (Mixed-Integer Programming) heuristics integrated into the HiGHS solver via a patched fork. The heuristics run during HiGHS's presolve phase and are compiled as object files linked directly into the `highs` library target.

**Reader-facing docs**, kept in sync with this file — update both when the behaviour they describe moves:
- `README.md` — positioning, the `mip_heuristic_suite` table, recorded benchmark results, build options.
- `CONTRIBUTING.md` — build/test/lint commands, the git hooks and how a checkout gets them, the clean-rebuild rule for patch-script changes, the benchmarking rules, the standing code-hygiene bar.
- `docs/REPRODUCIBILITY.md` — what is reproducible and what is not, and the exact PLATO reproduction protocol.
- `docs/RELEASE.md` — how a version is cut and published: the gates, the artifact archive (`bench/make_archive.py`), the DOI wiring and its ordering constraint, and the release checklist. Publishing, not reproducing — it references `REPRODUCIBILITY.md` and `CONTRIBUTING.md` rather than restating them.
- `docs/PARAMETERS.md` — every tunable `constexpr`. **Verified by ctest** (`docs_parameter_references`, via `bench/check_docs_refs.py`): renaming a documented constant fails the suite. Entries name symbols, never line numbers — line numbers drifted on essentially every refactor, which is why they were dropped. Don't reintroduce them.

## Build Commands

```bash
# Lint tools, once per checkout.  `.venv/bin` is the exact path
# cmake/Lint.cmake searches; without this the gates are never registered and
# ctest reports green having linted nothing.  Include pytest — the root
# CMakeLists prefers `.venv/bin/python`, so a venv without it unregisters
# `bench_python_tests` rather than falling back to the system interpreter.
# Include ruff for the same class of reason: both git hooks guard their ruff
# step on `[ -x "$VENV_BIN/ruff" ]`, so a venv without it skips Python linting
# silently while CI still gates on `ruff check bench cmake` — the hooks pass
# and CI goes red.
python3 -m venv .venv
.venv/bin/pip install clang-format==22.1.8 clang-tidy==22.1.8 ruff==0.16.3 pytest

# Configure (from repo root)
cmake -B build -DCMAKE_BUILD_TYPE=Release -DMIP_HEURISTICS_REQUIRE_LINT=ON

# Build
cmake --build build -j$(nproc)

# Run all tests, lint gates included
cd build && ctest --output-on-failure

# Fast inner loop: everything except the two lint gates
cd build && ctest -LE lint --output-on-failure

# Run a single test by name
cd build && ctest -R "execution-mode: flugpl objective" --output-on-failure

# Run tests matching a Catch2 tag
cd build && ./mip_heuristics_tests "[mode-matrix]"
```

The first build fetches and compiles HiGHS via FetchContent, which dominates
it; how long that takes is hardware-dependent (~48 s of compile at `-j32`).
Two things keep the *clean* rebuild that `pre-push` forces from costing that
every time:

- **ccache**, wired in `CMakeLists.txt` ahead of `include(cmake/FetchHiGHS.cmake)`
  so HiGHS's own targets inherit the launcher — a target reads the property at
  creation, so setting it afterwards would cache our four object files and miss
  the tree worth caching. Measured on a clean rebuild: 48.2 s cold, **0.92 s
  warm** at 367/367 direct hits. It does not weaken the clean-rebuild guarantee,
  because ccache keys on source content and a differently-patched tree misses.
  `-DMIP_HEURISTICS_CCACHE=OFF` opts out; a missing ccache is a status message,
  not an error. The launcher does **not** appear in `compile_commands.json`, so
  `cmake/clang_tidy_gate.py` and `.clangd` are unaffected — check that again if
  the CMake version moves.
- **`GIT_SHALLOW ON`** on both `FetchContent_Declare` calls: HiGHS 197 MB -> 49 MB,
  Catch2 45 MB -> 19 MB, since ~90% of the full clone is history nothing reads.
  One visible consequence: git sizes its abbreviated hash by object count, so a
  shallow tree's banner reads `Githash 04024d70` where a full clone reads
  `04024d701f` — the same commit at a different width. That was already
  anticipated (`same_build` in `check_vanilla_equivalence.py` compares the hash
  by prefix and `normalize_log` masks its width), and `make_archive.py` records
  one hash per config, so a single-binary campaign is unaffected. Do not
  "tighten" either into an equality check.

**The lint gates are ctest tests** (#101), labelled `lint`: `clang_format` and
`clang_tidy`, registered by `cmake/Lint.cmake` over `src/` and `tests/` only.
They add roughly 30 s to a full `ctest` run — `ctest -LE lint` is the fast loop
while iterating, and the full suite is the gate. `MIP_HEURISTICS_REQUIRE_LINT=ON`
turns a missing tool or a wrong major version into a *configure* failure instead
of a warning that scrolls past; CI sets it, and so should you, because the
default failure mode is silent. Tool versions are part of the contract:
clang-format's output changes between major releases, so the pinned 22.1.8 pair
from PyPI is what the gate is written against. clang-tidy's own exit status is
unusable here — HiGHS's `HighsMipWorker.h` contains a construct clang rejects
as a parse error and GCC accepts — so `cmake/clang_tidy_gate.py` wraps it and
judges first-party diagnostics itself. Never work around a tidy finding by
widening that wrapper's filter.

GPU acceleration: `-DMIP_HEURISTICS_CUDA=ON` enables CUDA for the PDLP solver used by Scylla. It **requires `CUDA_HOME`** to be exported (HiGHS's `FindCUDAConf.cmake` derives `CMAKE_CUDA_PATH` from it and uses that for the cudart/cublas/cusparse `find_library` hints and for HiGHS's CUDA include directory), and it **fails the configure** if nvcc or `CUDA_HOME` are missing, or if the `HConfig.h` HiGHS generates doesn't come out GPU-enabled — it does *not* fall back to CPU. That's deliberate: GPU vs CPU is a compile-time `#ifdef CUPDLP_CPU` in HiGHS's `CupdlpWrapper.cpp` with no runtime override, so a silent fallback yields a CPU binary indistinguishable from a GPU one at the command line. Build GPU into a separate tree (`cmake -B build-gpu -DMIP_HEURISTICS_CUDA=ON`) and confirm with `ldd build-gpu/bin/highs | grep -E 'cudart|cublas|cusparse'`. Omit the flag for a CPU build.

## Architecture

**Integration model**: Heuristics are compiled as a static object library (`mip_heuristics`) whose objects are injected into the HiGHS `highs` target. The HiGHS source is fetched at build time (v1.15.1) with patches applied from `third_party/highs_patch/`. Heuristics access HiGHS internals directly via `HighsMipSolver&`.

**No backward compatibility with older patch versions.** `apply_patch.cmake` refuses any HiGHS tree whose `mip-heuristics patch version` marker is not the current `PATCH_VERSION`, and does not attempt an in-place upgrade — no retired-identifier list, no rewriting an older option layout, no stripping a previous solution-source enum set. Bump `PATCH_VERSION` on any change to inserted text and clean-rebuild; that is the whole contract. The marker lives in `HighsOptions.h`, so it speaks only for that file: the two probes that survive are the ones for `HighsMipSolver.cpp`, which carries no marker and whose `heuristics::run_presolve` / `fpr_lp::run` idempotency sentinels are present in every layout the call sites have ever had. Retiring an option that appeared in an inserted *call site* means updating that file's probe to name it; retiring one that only appeared in `HighsOptions.h` means nothing but the version bump. The same stance applies to the harness: results trees must use the `<config>/seed<N>/` layout, and config names have no aliases.

**Bumping the HiGHS tag**: HiGHS renames `advanced` options across minor versions with no deprecation shim (`pdlp_scaling` → `pdlp_scaling_mode` and `pdlp_e_restart_method` → `pdlp_cupdlpc_restart_method` at v1.14.0, which left two dead option writes in `contested_pdlp.cpp` for months). Every `Highs` instance we build sets `output_flag=false`, so a rejected `setOptionValue` is completely silent — it reports failure only through the return status. After a bump, grep for `setOptionValue` and check each name against `_deps/highs-src/highs/lp_data/HighsOptions.h`, and prefer routing writes through a status-checking helper (`set_option_or_die` in `contested_pdlp.cpp`). Verifying that an option *exists* is not enough: check that the code path you're on actually reads it (e.g. `pdlp_scaling_mode` is consumed only by HiPDLP, never by cuPDLP-C).

**Heuristic entry points** — each has a standalone `run()` that HiGHS calls during presolve:
- `fpr` — Fix, Propagate, and Repair. DFS tree search that fixes integers, propagates bounds, backtracks on infeasibility, then runs WalkSAT/RepairSearch to fix remaining violations. `fpr_core.cpp` exposes two APIs: the one-shot `fpr_attempt` (used by scylla / fpr_lp / one-shot tests) and the `fpr_attempt_begin` / `fpr_attempt_step` / `fpr_attempt_finish` lifecycle (issue #77) that lets `FprWorker` pause an in-flight DFS at the per-call budget gate and resume it on the next call with state in `FprAttemptState` + `FprScratch`. The pause/resume mechanic is what avoids discarding work on long DFS subtrees; multi-attempt looping inside `run_attempt` lets fast workers fill the slice with new attempts (rotated through `kInitialFprConfigs` per `(worker_idx + attempt_idx)`) instead of idling. Sub-algorithms: `prop_engine` (bound propagation, with both forward propagate and a domain PQ for dynamic-var strategies — `repair_search` requires `e_pq_mark` threading on `RepairSearchNode` to keep the PQ consistent across its secondary backtracks), `walksat`, `repair_search`, `fpr_strategies` (strategy variants).
- `fpr_lp` — LP-dependent FPR (paper Classes 2–3) using root LP solution. Called during B&B dive (after RENS/RINS), not presolve. Draws from the **same LP-iteration budget as RENS/RINS** (`mip_heuristic_effort` envelope) and charges its work back — see the options section below. Gated by `heuristics::effective_flags(...).fpr`, i.e. it runs at any `mip_heuristic_suite` value naming `fpr` (`fpr`, `all`, `fj,fpr`, …) — `off` and every subset omitting `fpr` disable it. It runs arm-aligned parallel workers (`w % kNumLpArms`): each of `num_threads` workers is bound to an LP arm from the curated Class 2/3a/3b list; excess workers wrap around the arm list with distinct seeds for diversity. Its per-dispatch `build_setup` — CSC transpose, two reference LP solves, one `compute_var_order` per arm — is deadline-gated and charges what a bail already spent (#118; see the deadline paragraph below).
- `fj` — Feasibility Jump. Thin wrapper that delegates to HiGHS's built-in FJ implementation, run on continuous parallel workers.
- `local_mip` — weighted local search (MIP neighborhood search), run on continuous parallel workers.
- `scylla` — feasibility pump: alternates PDLP approximate LP solves with FPR rounding, progressive objective blending, and cycling perturbation. Runs N independent pump chains sharing a single `ContestedPdlp` instance (mutex-guarded `Highs` PDLP wrapper) so only one PDLP solve is in flight at a time. Workers that can't grab the PDLP mutex fall back to rounding against the most-recent *stale* snapshot so N-1 chains stay productive during a peer's solve (bounded by `kMaxStaleRounds` per worker before forcing a blocking solve; issue #76). Each chain owns its own warm-start, α_K decay, cycle history, RNG, and static FPR rounding strategy (`kFprConfigs[w % N]`). Runs on continuous parallel workers.

**Dispatch and parallel infrastructure** (`src/`):
- `mode_dispatch` — top-level presolve entry point. Reads `mip_heuristic_*` options and always runs the fixed chain via `run_sequential`: FJ → FPR → LocalMIP → Scylla one after another, each with its own effort budget and each on continuous parallel workers. The chain is a `constexpr` four-entry `HeuristicConfig` table (`{name, source_tag, flag, effort, budget_is_per_worker, patience, run}`, where `effort` is a pointer-to-member naming that heuristic's effort option and `patience` its absolute staleness threshold) and `run_sequential` is a filtered loop over it — adding or reordering a heuristic is a table edit (#94). There is one parallel runner; the deterministic epoch-gated mode was removed in #92. Reproducible runs come from `threads=1` plus a fixed `random_seed` — one worker per heuristic, no new option.
- `heuristic_context.h` — the common runner contract (#94). All four heuristics expose `size_t run(const ProblemView&, const HeuristicBudget&, ExecutionContext&, IncumbentSink&)`. `ProblemView` is the model + CSC transpose + derived `ncol`/`nrow`/`nnz` + a copy of the incumbent, built **once per dispatch** by `make_problem` in `run_sequential` and shared by the chain (each heuristic used to build its own identical copy; `mipdata`'s row-major buffers are frozen by `runSetup()` before dispatch). **Workers must read `problem.incumbent`, never `mipdata->incumbent`** (#98): submission is immediate, so a peer's accepted solution runs `addIncumbent` — whose `incumbent = sol;` rewrites that buffer element-wise, and reallocates it outright on the empty-to-sized transition — while a worker indexes the live vector. Read it *after* the pool, never instead of it: `IncumbentSink` seeds the pool from the incumbent and every accepted solution goes through the pool first, so `copy_best` is the thread-safe way to see a peer's find, and a worker rebuilt mid-dispatch (FJ does this on staleness) that skipped the pool would silently lose it. Anything else a worker reads out of `mipdata` has to be either frozen by `runSetup()` or snapshotted the same way; `fpr_lp` keeps its own copies in `LpFprSetup`, and `seed_pool` reads the live vector only because it runs on the dispatching thread before any worker starts. `ProblemView::binary` is the second such snapshot (#99): `addIncumbent` also runs `getDomain().propagate()` and `redcostfixing.propagateRootRedcost`, which tighten the root domain bounds that `HighsDomain::isBinary` reads, so workers classify columns from the snapshot — LocalMIP via `WorkerCtx::is_binary`, FPR/Scylla/fpr_lp via `FprConfig::binary_mask`, which any caller inside a parallel region must set. The one live `isBinary` read left is `bucket_by_type` in `fpr_var_order.cpp`, reached only through `compute_var_order`, which every caller now runs on the dispatching thread — `fpr::precompute_var_orders`, `fpr_lp`'s `build_setup`, and `scylla::precompute_config_var_orders`. That last one was added by #99: `ScyllaWorker`'s constructor used to compute its own order, and `scylla::run` rebuilds retired workers *inside* the parallel loop, so a rebuild read the live domain and called `cliquePartition` concurrently with `addIncumbent`'s `extractObjCliques` — which reallocates the clique table. Any new `compute_var_order` caller must stay on the dispatching thread for the same reason. `HeuristicBudget` is one heuristic's `total`/`per_worker`/`attempt_cap`/`stale`/`worker_stale` split from `make_budget`, which takes the staleness ceiling as an argument rather than deriving it (see the patience paragraph below). `ExecutionContext` carries worker count, base seed, and the two termination predicates — see the deadline paragraph below. `fpr_lp` takes only `make_exec`/`make_budget` — it keeps its own `LpFprSetup` for LP references and the shared `ContestedPdlp`.
- `incumbent_sink` — the only path from a worker to a solution. Owns the `SolutionPool`, the mutex around HiGHS's non-thread-safe `trySolution`, and the `kSolutionSource*` tag; workers call `sink.offer(obj, sol)` and never name their own tag. `run_sequential` re-tags via `set_source` between heuristics (legal only there — every parallel region has joined). It also counts accepted offers (`accepted()`, atomic): that counter moving across one heuristic's dispatch is the `found` field of its `[Heur]` line, since a worker's return value is its effort and nothing else.
- `effort_ledger` — the only place *in `src/`* that writes `heuristic_effort_used` or emits the `[Sequential]` / `[Heur]` lines (the patch adds one further `heuristic_effort_used +=` inside HiGHS's own `feasibilityJump()` — see `apply_patch.cmake` — live only at `suite=off`, and emitting no log line). `charge_presolve` for the chain; `charge_dive` for `fpr_lp`, which additionally depletes the RENS/RINS LP-iteration envelope. `EffortLedger::now_s()` is the solver's own clock (`HighsMipSolver::timer_`), not a raw `steady_clock`, so `[Heur] start_s/end_s` share an origin with HiGHS's own display-line time column. Nothing else in `src/` writes an upstream `HighsMipSolverData` counter.
- `worker_base.h` — `AttemptResult` (one attempt's effort + improvement flag) and `WorkerBudgetState` (per-worker effort / staleness / budget bookkeeping, embedded by composition into all four workers — `FprWorker` joined in #111 and arms only the staleness half, leaving `total_budget` at SIZE_MAX because the whole-dispatch ceiling belongs to the runner).
- `opportunistic_runner.h` — the generic continuous parallel loop every heuristic runs on.
- `contested_pdlp` — mutex-guarded `Highs` PDLP wrapper shared by all Scylla workers. One-shot `solve(modified_cost, warm_start, epsilon)` API holds the mutex for the full `changeColsCost → setSolution → run → getSolution` path, guaranteeing at most one PDLP solve is in flight (critical for cuPDLP GPU state). The solve's time limit is **not** an argument — the wrapper owns the deadline and reads what is left of it inside the lock (#117; see the deadline paragraph below). Also exposes `try_solve_or_snapshot(...)`: `try_lock` + fresh solve on success, or a lock-free `std::atomic<std::shared_ptr<const Snapshot>>` read of the most-recent completed solve on contention — lets N-1 Scylla workers keep rounding while one holds the mutex (issue #76). The in-flight counter is debug-asserted == 1 inside the critical section.
- `scylla_worker` / `pump_common.h` — Scylla worker class and shared feasibility-pump primitives (Mexi et al. 2023). Each worker is one `ScyllaWorker` (see `worker_base.h`) and runs its own chain of PDLP→FPR iterations.
- `fj_worker` / `fpr_worker` (inside fpr) — the FJ and FPR worker classes. `FprWorker` is declared inline in `src/fpr.cpp`; there is no `fpr_worker.*` file.

**Shared utilities** (`src/`):
- `heuristic_common.h` — `HeuristicResult`, `CscMatrix`, row violation, clamping, effort-budget and patience sizing. Not the deadline: that is `ExecutionContext` in `heuristic_context.h`.
- `solution_pool` — thread-safe top-K solution pool with crossover restarts. It is a **restart reservoir, not an incumbent store**: HiGHS's `addIncumbent` takes a solution only when it strictly improves the upper bound, and every accepted offer reaches it, so the pool's looser admission never loosens what the solve reports. That looseness is `kDiversityObjTolerance` — a full pool also admits a solution within 10% of the best when it is at least `kDiversityMinHammingFrac` from *every* entry — and it exists so crossover has diverse parents; an improving-only pool is a chain of near-identical vectors. The diversity path evicts the admitted offer's nearest neighbour **other than the best entry, which it may never evict**: it runs only on an offer the pool already considers dominated, so allowing it would spend the best solution on a worse one, degrading `copy_best` and the crossover's better parent until the pool refilled. Diversity is still measured against the best; only eviction skips it.

**HiGHS options** added or touched by the patch:
- `mip_heuristic_effort` — **vanilla semantics, vanilla default (0.05)**. This is upstream's B&B heuristic knob: `moreHeuristicsAllowed()` admits B&B-dive heuristics while `heuristic_lp_iterations < total_lp_iterations * mip_heuristic_effort` (plus an initial 10000-iteration offset). It gates RENS/RINS *and* `fpr_lp`: `fpr_lp::run` sizes each call to the remaining LP-iteration headroom of that envelope (converted at `nnz` effort-units per LP iteration, capped at `heuristic_effort_budget(nnz, mip_heuristic_effort)`) and charges all consumed work — reference-LP solves plus worker effort — back to `heuristic_lp_iterations`/`total_lp_iterations`, so fpr_lp competes with RENS/RINS for the same budget instead of drawing unaccounted work (fpr_lp skips entirely while `parallelLockActive()` — multi-worker B&B under `parallel=on` — because those counters are shared and it has no worker-local flush path). A patched binary at default options therefore matches vanilla's B&B heuristic budget exactly. (History: the patch used to raise the default to 0.30 and overload this option as the presolve budget — split in July 2026.)
- `mip_heuristic_fj_effort` / `mip_heuristic_fpr_effort` / `mip_heuristic_local_mip_effort` / `mip_heuristic_scylla_effort` — one effort budget multiplier per **presolve** heuristic (#110), each a double in `[0.0, 1e6]`; budget = `value * (nnz<<10)` — a multiple of vanilla HiGHS's own hardcoded single-thread FJ limit, so `effort = 1.0` means exactly one vanilla FJ budget and the patience option beside it is in the same unit (#116; it was `nnz<<12 * (value/0.05)` before, two historical constants multiplying to 81,920 that a reader had to know to compare the pair). The ceiling of `1e6` exists so #113's calibration probe can hand a heuristic a budget that *cannot bind*, leaving the wall clock as the single stopping rule (`docs/PARAMETERS.md`, "A budget that cannot bind"). Budget is derived in `run_sequential` from the model's `nnz`. They are **independent**: raising one heuristic's budget no longer lowers the others'. That is the whole point — the retired shared envelope, split by `kWeight*` constants proportional to geomean `effort_per_ms`, made "what is a good budget for LocalMIP?" unanswerable without confounding it with FPR and Scylla, and left FJ unreachable from any option at all (measured flat to five significant figures across a 20x sweep). **FJ's option sizes one worker's allowance**; the other three size a whole dispatch, which `make_budget` divides by N. The `budget_is_per_worker` flag in `kChain` is the only place that distinction lives (spelled out because `per_worker` in that translation unit already means `HeuristicBudget::per_worker`, a size_t budget rather than a flag). Defaults are **measured** (#113): fj `2.84`, fpr `7.672`, local_mip `29.232`, scylla `1.136`, each the median budget that reached a dispatch's last incumbent improvement over the 233-instance PLATO list at 16 workers — see `bench/ablation_effort/` for the derivation and the artifacts it came from. They were inherited before that, from the pre-#110 split: fj `0.0125` = `nnz<<10` per worker, exactly vanilla HiGHS's hardcoded single-thread FJ limit; fpr `0.0884`, local_mip `0.1821`, scylla `0.0296` = `0.30 × w/Σw` for the retired weights 2.99 / 6.16 / 1.00. The measured vector lands within a factor of two of every one of those and within 8% for FPR, so the inherited numbers were sane; the directional change is **double LocalMIP, halve Scylla**. `tests/test_smoke.cpp` pins all four, because they live in `apply_patch.cmake` where nothing else checks them. **They approximate the retired scheme; they do not reproduce it, and no scalar can.** The old envelope handed a heuristic `budget × max(1 − N/(80e), ¼) × w/Σw_enabled`, which depends on two runtime facts a constant cannot see: the worker count `N`, and which *other* heuristics the suite enabled. Dropping the worker-count term makes `suite=all` 1.04x the old budget at `N=1`, 1.33x at `N=6`, 2x at `N=12` and 4x from `N=18` (where the old quarter-floor capped the FJ deduction); dropping the enabled-set term cuts a *single-heuristic* suite — which used to hand its one heuristic the whole envelope — to 0.29x / 0.61x / 0.10x for fpr / local_mip / scylla, which is the configuration a per-heuristic sweep runs in. FJ is the one exact case, at every `N` and every suite. The anchor is a choice, not a constraint: the deviation is smallest at the low worker counts the tests actually run at (1–2 on CI, `(hardware_concurrency()+1)/2` locally), and erring high is the cheap direction once patience is absolute (#111) — an over-large budget is truncated by a gate that fires, an under-large one is a hard cap nothing recovers. The full accounting lives in `apply_patch.cmake` beside the defaults, with the calibration-facing version in `docs/PARAMETERS.md`. Treat all four as the starting point of #106's calibration, not the result of one. Note: LocalMIP's reported effort folds in the cold-start construction sweep (Phase B greedy sweep from `local_mip_construction.cpp`, charged in coefficient-access units to match `WorkerCtx::effort`) on dispatches where pool and incumbent are both empty; the cheap Phase A column-write loop is excluded from the normal-path total for unit consistency, but a small `ncol` charge is still reported on the degenerate `nrow==0 || max_effort==0` early exit. `effort_per_ms` remains the cross-heuristic throughput comparison (see Observability below); it no longer calibrates anything, since there are no weights left to set.
- `mip_heuristic_suite` — **the** heuristic selector, default `all`. The value is either one of the two whole-value aliases `off` / `all`, or a **comma-separated list** of the heuristic names `fj`, `fpr`, `local_mip`, `scylla` (#112), so all fifteen non-empty subsets are expressible: `fj,fpr,local_mip` is the composition the recorded PLATO table was measured at. Order is irrelevant, whitespace around a token is trimmed, repeats are harmless. Replaced `mip_heuristic_preset` and the three `mip_heuristic_run_*` bools in #93. It also gates `fpr_lp` (via `heuristics::effective_flags`), so any value not naming `fpr` disables the dive-time heuristic too. **`heuristics::effective_flags` in `src/mode_dispatch.cpp` is the single place the string becomes four booleans** — the dispatcher and `fpr_lp` both call it, and the legal names are `kChain`'s own `name` field rather than a second table, so a suite token cannot drift from the `[Heur] name=<n>` trace it produces. `off` is an alias for the *whole* value and never a token in a list (`fj,off` is rejected): the patch compares `mip_heuristic_suite == "off"` verbatim in two places, so a value that selected nothing without being that exact string would run no heuristic at all — not even HiGHS's own FJ, which `off` deliberately keeps. `setLocalOptionValue` strips *spaces* — only spaces — from both ends of a string option's value and lower-cases it before storing (the options-file loader strips tabs, newlines and quotes first), which is what makes that exact comparison safe on both sides of the patch boundary: whatever neither strips misses `== "off"` identically in our parse and in the patched tree. HiGHS does not validate the *value*, so an unknown one is accepted by `setOptionValue` and caught at solve time, where the dispatcher warns — **naming the offending token**, because one typo inside an otherwise valid list silently promotes the run to all four — and fails open to all four. An empty value or a stray trailing comma is an unrecognised token, not a silent `off`. **`off` is the "our four presolve heuristics disabled" ablation, and that is all it is.** It exists so the chain can be tested with nothing of ours running; it is **not** a vanilla baseline and must never be used as one (see the benchmarking note below — the baseline is always a separately built unpatched binary). `suite=off` restores HiGHS's own standalone FeasibilityJump call site, so `off` alone still runs HiGHS's FJ; `off` plus `mip_heuristic_run_feasibility_jump=false` is the nothing-at-all configuration, and it is the one `bench/check_vanilla_equivalence.py` compares against an unpatched binary (#147). That restoration made `off` *incidentally* close to vanilla from #93 — incidentally, not by design: the FJ it runs is our copy, which already differs at `log_dev_level=3` (the per-bump `Reached a local minimum.` line is gone), and the still-open #139 will end any resemblance by fixing two upstream FeasibilityJump defects unconditionally. `tests/test_native_fj.cpp` pins what `off` does promise: the native call site runs and charges `heuristic_effort_used`, and stops doing both when `mip_heuristic_run_feasibility_jump=false`.
- `mip_heuristic_presolve_only` — bool, default `false` (#106). After the presolve chain completes, exit the solve **before the root LP**, keeping the incumbent. Reports `HighsModelStatus::kSolutionLimit`, which is what HiGHS itself assigns for a user-configured search-size limit and — unlike `kNotset`/`kInfeasible` — is *not* rewritten by `cleanupSolve`, which would otherwise stamp `kOptimal` on a solve that never computed a dual bound. So a presolve-only run reports `Dual bound -inf`, `Gap inf`, `Nodes 0`, `LP iterations 0`, CLI exit **1** (`HighsStatus::kWarning`), and a finite `Primal bound` with real incumbent display rows when the chain produced something. `run_benchmark.py` accepts exit 1, so these land in a normal `.log`. This is the mode #113's screen runs in: ~25x cheaper than a full solve, and the only way to measure the chain without B&B diluting it.
- `mip_heuristic_fj_patience` / `mip_heuristic_fpr_patience` / `mip_heuristic_local_mip_patience` / `mip_heuristic_scylla_patience` — **a double in the same unit as that heuristic's effort option** (#116), defaults 0.71 / 1.918 / 7.308 / 0.284 — measured (#113), each the p95 wait for the next incumbent improvement clamped to a quarter of that heuristic's ceiling, which is why every one of them is exactly `0.25 x effort`, and the quarter is what bounds a barren dispatch; they were 256 / 2048 / 4096 / 512 when the options landed (#106), and were spelled `mip_heuristic_<name>_stall` until #116 renamed them **with no alias** (the parameter is a floor on spend, not a state the search is in). See the patience paragraph above for scope and for what `0` means.
- `mip_heuristic_run_feasibility_jump` — upstream's own FJ switch, and the one pre-existing option the patch still reads. `false` disables FeasibilityJump at every suite value: at `off` it gates HiGHS's native call site, elsewhere it gates ours. `suite=off` plus this set to false is the pure patch-overhead configuration.

**Patience is absolute, and it reads incumbent improvements** (#111, #116). Every presolve heuristic stops early when improvement-free effort crosses a threshold, at two levels — a runner-level gate over the whole dispatch (`ContinuousLoopState::effort_since_improvement` against `HeuristicBudget::stale`) and a worker-level gate in `WorkerBudgetState`. **A gate has two operands and both were broken.** (1) The *threshold* was `total_budget >> 2` in three of the four, which cannot bound over-budgeting: doubling the budget doubles the tolerance, so the gate never fires relatively sooner. FeasibilityJump's `nnz << 8` was the exception and is the model. It is now one **option** per heuristic — `mip_heuristic_<name>_patience`, a double in the same unit as that heuristic's effort option, read through `kChain` (#106; they were `kStallPerNnz<H>` constants in the heuristic headers until then, which meant the axis could not be swept without a rebuild, and were spelled `_stall` until #116). The four are **not** comparable across heuristics, because only each heuristic knows what its own effort counter counts. **`0` means no gate at all** — unbounded, returned ahead of the clamp — not "give up immediately"; that is what lets #113's probe measure a heuristic with nothing stopping it. `patience_threshold(nnz, per_base, budget)` in `heuristic_common.h` applies one, **clamped to `budget / kPatienceCeilingDivisor`, a quarter, not to `budget`** (#116): a patience at or above the ceiling fires exactly at exhaustion, which is behaviourally identical to no gate and reported nowhere, and that is the *common* case for an honestly measured value — #113's p95 exceeds the ceiling on three of four heuristics, FJ's by 4,400x. A quarter is FJ's own shape and is exactly where all four shipped defaults sit, so the clamp moved no default. `run_sequential` sizes the runner-level gate (multiplying by the worker count for FJ, whose option's scope is per-worker like its effort option) and `make_budget` divides it by N into `worker_stale`. Scylla is the one documented deviation: it takes the dispatch-level `stale` as its worker threshold, because its per-worker counter is charged the PDLP cost already divided by N. (2) The *improvement signal* was wrong twice. It was each worker's own "I beat my own best", which restarts at infinity on every rebuild — so a rebuilt worker cleared the dispatch's staleness by rediscovering a solution the pool already held. #111 pointed both gates at `IncumbentSink::offer`'s **acceptance** verdict and called that "the project's single definition of production", explicitly ruling a stricter signal out of scope. **#116 reverses that for the gate**, on #113's measurement: the pool keeps a top-K, so a heuristic that merely beats its own worst entry resets staleness forever, and over 233 instances at 16 workers FPR earns ~3.3M acceptances against 590 incumbent improvements (local_mip ~3.3M/24,598, scylla 367,801/374, fj 1,557/297). Five orders of magnitude — a patience calibrated on improvements, which is the only honest way to calibrate one, cannot be spent against a gate that resets on acceptances. So `offer` returns **two** facts (`IncumbentSink::OfferResult{accepted, improved_incumbent}`, still `[[nodiscard]]`): gates read `improved_incumbent`, decided inside `SolutionPool`'s own lock against the best objective the pool has ever accepted — the only race-free place, since a worker may not read a solver field (#98/#99), and a **monotone watermark** rather than `entries_.front()`, which the diversity-replacement path can evict, degrading the pool's best where the solve's never degrades — while `accepted()`, `[Heur] found` and `[HeurSol] accepted` keep their pool-acceptance meaning, because `bench/parse_highs_log.py` and external tooling depend on it. Returning a struct rather than repurposing the bool is deliberate: it makes every gate site name which fact it reads. **`CMakeLists.txt` puts `-Werror=unused-result` on `mip_heuristics` and `mip_heuristics_tests`**, without which a re-drop is only a warning — nothing here passes `-Werror` and the clang-tidy gate cannot see `clang-diagnostic-*`, since `.clang-tidy` opens with `-*`. Keep that flag on our two targets and off HiGHS's. The two deliberate discards (`fpr_lp`, LocalMIP's cold-start publish) are spelled `static_cast<void>` with a reason. **Only the gate's operand moved** — LocalMIP's `best_objective_`/`steps_since_improvement_` and FJ's internal `effortSinceLastImprovement` are the local search's own bookkeeping and still use the local notion. **All three parts were needed**: over a 20x sweep of the effort option at `threads=1`, seed 0, `fpr/flugpl` is 19.98x before, 19.98x with the threshold fixed, 1.03x with #111's signal, 1.80x now; `fpr/egout` is 19.98x / 19.98x / 19.98x / **1.82x**, which is the case #111 recorded as unfixable without exactly this change and `tests/test_patience_gate.cpp` now asserts on. Current ratios: fpr 1.18-2.26x across egout/flugpl/p0548/gt2, fj 1.50x, scylla 1.00x, local_mip 7.81x on p0548 seed 0 and still the loose one. **Read a rising ratio carefully**: a stricter signal retires a worker sooner at *both* ends of the sweep and the low end falls further because it was budget-bound, so `fpr/p0548` goes 0.89x → 2.26x on strictly less work at both points (4.23M → 1.62M low, 3.77M → 3.68M high). The ratio says whether the gate binds, not how much it saves. Scylla has a granularity floor no constant can cross: one attempt charges a whole PDLP solve (`iters x nnz`), several times the ceiling, and `attempt_cap` does not govern a solve once started — do **not** try to fix that by clamping `attempt_cap`, which is measurably ineffective (`dcmulti` has `attempt_cap` 15x below the ceiling and still charges ~1.35M per attempt). The four defaults are **measured** (#113) rather than provisional; #116's own last word is that the probe should be re-run now that the solver gates on the same signal the calibration is taken on, and that re-run was held **until every code issue affecting it landed** — it is a ~9 h overnight window, and a run taken between merges is superseded by the next one. #119 in particular mis-binned a setup-abandoning dispatch as barren, which is the population the patience side rests on. That precondition is now **satisfied**: #116, #117, #119 and #118 are all in, so the re-run is unblocked and the shipped numbers stay provisional until it has been taken. `bench/ablation_effort/README.md` carries the precondition beside the numbers it qualifies. `fpr_lp` is out of scope in all of it and keeps `worker_budget >> 2` and its own signal.

**The wall-clock deadline is bounded by a polling interval, not by an attempt** (#114). `ExecutionContext` exposes two predicates, and which one a caller may use is a thread-safety fact, not a preference. `past_deadline()` is `timer_.read() >= time_limit` alone: `HighsTimer::read()` is `const` and writes nothing for the solve clock, so **any worker thread may call it** — that is what lets every heuristic poll the deadline from inside its own inner loop. `terminated()` adds `terminatorTerminated()`, which *writes* `mipsolver.termination_status_` when a terminator is attached, and is therefore still seat-holder-only via `ContinuousLoopState`; `run_sequential` also calls it between heuristics, where every parallel region has joined. There is no longer an exception to that rule — FPR's inner loop used to call `terminated()` from its own thread and now calls `past_deadline()`, which is the half it needed. The cadences: FJ per upstream callback (`CALLBACK_EFFORT` = 500000 effort units), LocalMIP every `kTermCheckInterval` steps, FPR per inner attempt *and* every `kDeadlinePollNodes` DFS nodes and every RepairSearch node (#117), Scylla per pump iteration — both of those need the *scalar* remaining time to hand a sub-solver rather than the predicate, and both now read it off a `Deadline`: `ContestedPdlp` inside its mutex (#117), `fpr_lp`'s reference LP solves through `Deadline::remaining()` (#118, which replaced the `time_limit - timer_.read()` those solves used to inline — the same clock read, but a second spelling of the deadline in a file whose caller could not then tell an expiry from a failed solve). The runner polls it unconditionally on every iteration too (`ContinuousLoopState::should_stop`), which is what stops a worker that ended its attempt *on* the deadline from spinning on empty attempts. **Why this was not enough before**: the only check was the runner's, between attempts, and one attempt is `attempt_cap` = `total / (10N)` — proportional to the effort option. Tight at the shipped defaults, worthless at `effort=1.0`, where FJ ran 1.4-2.0x past a 60 s limit and twice to an external SIGKILL at 3.5x, silently truncating the rest of the chain (`run_sequential` skips a heuristic once `exec.terminated()`). Two things this does **not** do: it does not un-truncate the chain — a heuristic that legitimately spends the whole limit still leaves its successors nothing — and it does not remove Scylla's floor of one whole PDLP solve, which no constant can cross. It also narrows reproducibility: a run whose deadline binds is wall-clock dependent even at `threads=1`, so a high-effort measurement run needs a limit its chain does not reach. **FJ's per-worker solver construction is still unbounded** — `createRowwise` plus `addVar`/`addConstraint` plus `init`'s `resetMoves`, before the first callback can fire — and is deliberately out of scope; a deadline in the callback cannot bound it.

**A poll bounds the overrun at one indivisible work unit, and #117 is what bounds *that* unit** for FPR and Scylla, the two whose units were coarsest. Three things were unbounded and are now not. (1) **The DFS.** `fpr_attempt_step` ran until `effort_remaining`, which every caller sizes from its effort option, so one call could run for minutes; it polls a `Deadline` every `kDeadlinePollNodes` nodes and pauses at `kBudgetGate` when it fires. This is shared code, so it bounds FPR's own attempts, Scylla's per-round FPR rounding and `fpr_lp`'s in one place. (2) **Phase 3.** `fpr_attempt_finish`'s entry to RepairSearch/WalkSAT is deadline-gated — the DFS's own poll does not cover an attempt that reached a leaf *at* the deadline — and `repair_search` polls per node, one node being two propagation fixpoints. (3) **The dispatch setup**, which was the whole of the measured overrun and is *independent of every option*: `precompute_var_orders` (8 orders, FPR) and `ContestedPdlp` construction plus `precompute_config_var_orders` (5 orders, Scylla) run sequentially before any worker exists, measured at 34.5 s and 20.7 s on `rail02`. Both now check the deadline between orders and return 0 from `run` with an incomplete table rather than finishing the list. On `rail02` at a 20 s limit this took FPR from 38.1 s to 22.3 s and Scylla from 28.7 s to 20.9 s.

**#118 is the same setup fix for `fpr_lp`**, whose dive-time setup #117 left ungated because all of its evidence was presolve-only runs: ten `compute_var_order` calls (one per LP arm) plus two reference LP solves, sequential on the dispatching thread, sized by nothing. `build_setup` polls between arms and around each solve. Two things make it *not* a mechanical copy. (1) An expiry there used to be **masked**: the reference solves return an empty vector once the clock has passed, the `ac_ptr`/`zv_ptr` fallbacks read that as "LP failed, use the full-obj solution", and the setup built all ten orders anyway — so its bounded half hid its unbounded half. Polling the clock rather than testing the vector is what separates the two. (2) **A bail owes the envelope.** `fpr_lp` charges its work back to the shared RENS/RINS LP-iteration counters, so a setup abandoned after a reference solve has already spent iterations that must still be booked, and `std::nullopt` cannot carry them out. The setup therefore returns a `SetupResult` — the optional setup, `lp_iterations` spent whether or not one came back, and `deadline_bail` — and `fpr_lp::run` charges through `charge_dive` on exactly one of two disjoint paths: the bail books `effort=0` plus whatever the solves cost (leaving a visible `[Heur] name=fpr_lp phase=dive` line, which is also which reports `abandoned_setup=1`, the field that keeps it out of #113's barren population), the normal path books once at the end. The model-shape and LP-status skips consume nothing and stay silent, as before. Nothing is cached across dives, so the next dive re-pays only for the work it redoes and no path can charge another's. **The invariant this deliberately retires** is the one that used to sit above `build_setup` — "all nullopt exits happen before the reference-LP solves" — which was what made a bare optional safe. There is no dive-time measurement behind any of this: it is #117's defect in the same shape, fixed by analogy, and the bundled instances are too small to time it.

`Deadline` (`src/deadline.h`) is the poll in the form a *sub-algorithm* takes it — a `const HighsTimer*` and a limit, null when the limit is infinite — for the layers below a runner that have no `ExecutionContext`: `fpr_core` is reached from `FprWorker`, `ScyllaWorker` and `fpr_lp`. `ExecutionContext::deadline()` and `deadline_of(mipsolver)` are the only two ways to build one, so a sub-algorithm cannot stop against a different clock or limit than its runner. **The PDLP solve's time limit is not a parameter** (#117): `ContestedPdlp` owns the deadline and reads the remaining time *inside* its mutex, because a caller computes a value and then blocks for the length of a peer's whole solve — Scylla's forced-blocking path every `kMaxStaleRounds` was exactly that — and a solve entered past the deadline returns an empty `SolveResult`, whose `kError` default retires the chain through `absorb_fresh_solve`. Upstream detail worth knowing: `CupdlpWrapper.cpp`'s `getCupdlpParams` computes a remaining-time adjustment and then assigns the *unadjusted* `options.time_limit` to `floatParam[D_TIME_LIM]`. That dead adjustment is load-bearing in our favour — it subtracts the wrapped `Highs` instance's *accumulated* run time, which would zero a late solve's limit — so a HiGHS bump that fixes it changes what our per-solve limit means. The residual floors, all documented in `docs/PARAMETERS.md` ("What bounds the deadline's tightness"): one propagation fixpoint, one `compute_var_order` (the largest of them, and it scales with the model — 2.2 s on `rail02`, ~9 s on `bab6`), one PDLP solve including the wrapped `Highs::run`'s own LP setup — plus, on the Scylla side, `ContestedPdlp`'s own LP build, which is ahead of the first deadline check and measured a budget-independent ~11 s on `bab6` — and FJ's worker construction above.

**Observability**: at `log_dev_level=3` `EffortLedger::book` (see `src/effort_ledger.cpp`) emits one `[Sequential] heur=<name> effort=<N> wall_ms=<X> effort_per_ms=<R>` line per presolve-chain heuristic per solve, plus one per `fpr_lp` dive dispatch (new in #94 — it used to do the work and report nothing). `bench/parse_highs_log.py` parses both. Keep the four presolve heuristics and `fpr_lp` apart when comparing rates: they draw from different budgets. A budget measurement runs on `bench/instances_small.txt` at `threads=16` — both are part of the measurement. `effort_per_ms` is a throughput and Scylla scales sublinearly in workers (PDLP mutex) where FPR/LocalMIP scale near-linearly, so the worker-count factor does not cancel in the ratios: the same binary on the same set gives local_mip:scylla = 4.68 at 16 workers and 2.81 at 6.

One further line at the same level, `key=value` with a stable leading token:

- `[Heur] name=<n> phase=<presolve|dive> start_s=<S> end_s=<E> effort=<N> wall_ms=<X> effort_per_ms=<R> found=<0|1> nnz=<Z> abandoned_setup=<0|1>` — same emission site as `[Sequential]`, one alongside each. It carries what `[Sequential]` cannot: *when* the heuristic ran on the solver clock, which side of the patch boundary it ran on, whether it produced anything, and whether it ran at all. This is the line the per-heuristic budget calibration reads. `[Sequential]` stays alongside it because external tooling parses it.
- `abandoned_setup` (#119) is the difference between a heuristic that searched and produced nothing and one that **never searched**: #117 made the sequential setup (`fpr::precompute_var_orders`, `scylla::precompute_config_var_orders`, and `fpr_lp`'s own `build_setup` since #118) give up when the wall-clock deadline has already passed, and such a dispatch booked an `effort=0 found=0` line byte-identical to a barren one. The #113 calibration bins barren dispatches to estimate patience, and a setup bail is only possible on the large, hard instances — so the mis-binning landed exactly where the estimate is most sensitive. **Three log shapes must stay distinguishable**: no `[Heur]` line at all is a killed run, `abandoned_setup=1` is a bail, and the field absent or `0` is a dispatch that ran. The field is emitted unconditionally on **both** the `charge_presolve` and `charge_dive` paths, so an *absent* field means one thing only — a log written before #119 — and `HeuristicSample.abandoned_setup` is `None` there rather than `False`, since the distinction is unobservable on such a log rather than known-absent. **There are two channels from a bail site to the ledger, and which one a heuristic uses follows from whether it books itself.** The four presolve heuristics are on the shared runner contract, so theirs is its return type — `DispatchOutcome` (effort + flag) in `heuristic_context.h`, replacing a bare `size_t`, booked by `run_sequential`. `fpr_lp` is **not** on that contract: it books its own dispatch, so its bail reaches the line as an explicit `charge_dive` argument and by nothing else (#118). That argument is deliberately **not defaulted** — it was, as scaffolding while #118 and #119 landed separately, and the default is gone precisely so a future dive-shaped caller cannot inherit `false` without considering the question. **Never infer the bail from `effort == 0` plus an expired deadline**, in a log or in process: a dispatch entered with a millisecond left constructs its workers and exits at zero effort without ever bailing in setup. Only the bail site knows, which is why the flag is returned rather than reconstructed.
- `[HeurSol] name=<n> dispatch=<i> worker=<w> effort_at=<E> wall_ms=<X> obj=<O> accepted=<0|1>` — one per **accepted** `IncumbentSink::offer`, at `log_dev_level=3` only (#106; narrowed to acceptances in #113, when a clock-bound probe run measured FPR offering ~11k/s on a small model — 327k lines and 36 MB from one 30 s run, 65% of a probe tree, for lines no consumer reads, since the productive/stale split, the gap distribution and every hard-tier verdict all filter to `accepted`. The field stays in the format: the parser requires it and older logs carry both values. What is gone is the raw offer rate; anything wanting it wants a counter in `[Heur]`, not a line per offer). The intra-dispatch view `[Heur]` cannot give: it yields productive effort (charged effort at the last accepted offer), stale effort, and the inter-acceptance gap distribution that calibrates a patience. `dispatch` is a **process-global** counter — unique per dispatch, never dense or zero-based per solve — so group on `(name, dispatch)` and bind to the closing `[Heur]` line via `HeurSolSample.heur_index`, which is **the supported binding**; re-deriving it is how three of four heuristics silently vanish. `effort_at` is monotone only within a `(name, dispatch, worker)` triple, and is that heuristic's own unit. Both `[Heur]` and `[HeurSol]` parse as **key=value**; `[Sequential]` stays positional because external tooling reads it.
- `[Heur]` carries `nnz=` (#106), from `mipdata->ARindex_.size()` — the post-presolve MIP matrix the effort and patience options are denominated in. It exists because **`log_dev_level=3` suppresses the model header the parser used to read**: the one-line `MIP <name> has ... nonzeros;` form is absent from every level-3 log and present in every other one, so `[HeurSol]` and the old `num_nonzeros` path were mutually exclusive, making the whole calibration unreachable. The level-3 `Rows/Cols/Nonzeros` block is *not* a substitute — it is the pre-presolve model.
- The ledger times against HiGHS's own solver clock (`HighsMipSolver::timer_`), so `[Heur]` windows share an origin with HiGHS's own display-line time column. That clock is **not** monotonic — `HighsTimer` bottoms out in `high_resolution_clock`, which libstdc++ aliases to `system_clock` — so a wall-clock step can produce a negative `wall_ms`. The bench regex accepts the sign so such a sample surfaces instead of silently vanishing.

`effort_per_ms` measures *charged* effort, not useful work, so it is **not** a valid before/after metric for a change that alters how much effort a unit of real work charges — only for comparing heuristics against each other at fixed code (its calibration job). Removing redundant work usually *lowers* it: the measured A/B for #89 (six `bench/correctness_check.py` instances, seeds 0-2, 12 workers) has the incremental structures at local_mip 400k effort/ms against 1.13M for a naive-sweep build, while the same runs do 19,079 LocalMIP steps/ms against 1,876 — a 10x throughput *gain* that the effort rate reports as a 2.8x loss, chiefly because a naive feasible step charges a full `nnz` recheck it did not need. Measure real work units (LocalMIP steps, FPR DFS nodes per ms) when A/B-ing a hot-path change.

**Testing**: Catch2 v3. Tests use `.mps` instances from HiGHS's own `check/instances/` directory (path injected via `INSTANCES_DIR` compile definition). Characterization tests verify known-optimal objectives. (See the testing override near the top of this file — we do not use GoogleTest.)

**Benchmarking**: `bench/` has scripts for MIPLIB benchmarks — `run_benchmark.py` runs instances, `analyze_results.py` parses results. The MIPLIB collection itself is **not** located at a fixed path: `bench/download_miplib.sh` and `run_benchmark.py --data-dir` share a search path — explicit argument, then `$MIPLIB_DIR`, then `~/data/miplib`, then `/tmp/miplib` — and the first directory holding more than 200 `.mps.gz` files wins. It is 3.5 GB, so it lives once per machine outside every checkout, and `/tmp` is probed (an existing copy is reused) but never written to (it does not survive a reboot). **That search path and its >200 threshold are defined twice, once in bash and once in Python**, and drift between them is silent and expensive — the downloader writes one directory while the benchmark reads another. Three tests in `bench/test_run_benchmark.py` parse the shell script and assert both against the Python constants; keep them passing rather than editing one side alone. Don't pass `--threads` (or set `threads=` in an `.opts` file) unless asked — let HiGHS use its default; forcing `threads=1` collapses each heuristic to a single worker (the right setting for reproducibility, the wrong one for a throughput benchmark). **The vanilla baseline is always a separately built unpatched binary** (`--vanilla-binary`, matching tag). Two binaries is the design, not a preference or a fallback: `suite=off` is the "our heuristics disabled" ablation and is not a vanilla proxy. **`run_benchmark.py` enforces that** (#147): `vanilla` is no longer a `CONFIG_SUITES` entry at all — it names a binary, not a suite value, and carries no options — `build_plan` raises when the config is asked for without `--vanilla-binary`, and `check_vanilla_binary` runs the named binary **with no arguments** before the first solve, refusing it if the banner carries `mip-heuristics patch active` or reports a version other than the `GIT_TAG` in `cmake/FetchHiGHS.cmake`. The no-argument invocation is the whole trick: `--version` never reaches `highsLogHeader`, so it prints neither the marker nor the `Running HiGHS <v> (git hash: <h>)` form — a probe there would silently pass a patched binary. Only the *version* decides anything in that banner; the git hash is captured for a manifest and compared by nothing, which is why `BANNER_RE` accepts `[^)]+` there rather than `\w+` — HiGHS sets `GITHASH` to the literal `n/a` when configured outside a git repository, so a distro package or a build from the release source archive would otherwise be refused for "printing no HiGHS banner" in a message quoting that banner. `check_vanilla_options` is the second half of the same pre-flight: `--extra-options` applies to **every** config, and the vanilla one is an unpatched binary with none of the ten options the patch adds, so `--extra-options mip_heuristic_fpr_effort=1.0` over the default `vanilla all` pair used to fail every vanilla instance at solve time and leave `run_plato.sh next` relaunching a campaign that could not advance. It asks the binary one key at a time (HiGHS stops reading an options file at the first unknown key, so one probing run names one offender) rather than filtering on a `mip_heuristic_` prefix — `mip_heuristic_effort` and `mip_heuristic_run_feasibility_jump` are upstream's own and legal on both binaries, and a hardcoded list of the other ten would need editing on every option change. `run_plato.sh` lost its fallback to `$BINARY` in the same change and refuses instead; the empty `--vanilla-binary` it may now pass is read as "not given", the same convention `--data-dir` uses. History, because the reasoning changed twice and only the conclusion held: before #93 the patch hard-disabled HiGHS's standalone FJ call site, making `off` *weaker* than vanilla; #93 handed that call site back, making `off` incidentally close to vanilla, which `bench/check_vanilla_equivalence.py` proved against an unpatched binary (identical objective, node count, total and heuristic LP iterations, empty normalized log diff; 12/12 on the six bundled instances × 2 seeds); it was never a designed property, the open #139 will end it outright, and #147 re-pointed that check at the configuration where **both sides disable FeasibilityJump** (`suite=off` plus `mip_heuristic_run_feasibility_jump=false` against upstream's own switch), which is the part still worth proving — that injecting the heuristics moves neither presolve, nor B&B, nor the LP path. What the narrowed check no longer covers is pinned by `tests/test_native_fj.cpp` instead. A run the harness had to SIGKILL (HiGHS checks its clock between work units, so one long simplex solve at the root can pass `time_limit` without returning to look) is kept as a **truncated `.log`**, not discarded: `run_benchmark.py` keeps the partial stdout and appends a `TIMEOUT: process killed after Ns` marker, which `parse_highs_log.py` turns into `killed` and a `Killed (timeout)` status, and `analyze_results.py` lists under "Killed runs". Those logs still score correctly — T1st and the primal integral read the incumbent lines, never the Solving report the run never reached — and are deliberately *not* retried on resume, since rerunning reproduces the same hang. Only a kill before the binary printed anything becomes a `.log.err`, which is the shape that does get retried. Patched binaries self-identify with a `mip-heuristics patch active` line right after the version banner (injected by `apply_patch.cmake`) — the version/githash banner alone is identical between patched and unpatched builds of the same tag (at equal clone depth — see the `GIT_SHALLOW` note in Build Commands for why the printed width, not the commit, can differ).

`run_benchmark.py`'s config surface (#96) is exactly one entry of `CONFIG_SUITES` per `mip_heuristic_suite` value, with no aliases, plus the one name that is *not* a suite value: `vanilla`, which selects the external unpatched binary and no options (`KNOWN_CONFIGS` is the union, and `resolve_config` raises against it). Since #112 that includes the ten pairs and triples, named with **`+` where the suite value uses `,`** (`fj+fpr` → `fj,fpr`): a comma is legal in a directory name but not free in a generated table or in LaTeX. Subset names list heuristics in chain order so one subset has exactly one spelling (`fpr+fj` is not a config). **`config_options` raises on an unknown config name**; it used to return `{}`, so `--configs patchd` produced a fully populated, plausible-looking, completely meaningless results tree. A config name carries **no budget of its own** — every heuristic runs at its shipped default, and moving one for a run goes through `--extra-options`. The `<config>@e<V>` suffix and `--budget-sweep` that used to express a budget ladder were removed once the calibration moved to a presolve-only screen driven by a parameter-vector target runner: a ladder of config names is not how any current stage varies a parameter, and two spellings for "which options does this run use" is one too many. `resolve_config` is now just the unknown-name raise, and `build_plan` remains the single place a name's two consequences — which binary, which options — are chosen together; choosing them at separate use sites is how a name picks one branch's binary and the other branch's options. A run that solved but ignored its configuration is routed to `<inst>.log.err` like a non-solving exit: HiGHS accepts an unknown `mip_heuristic_suite` *value* and `run_presolve` fails open to all four heuristics with a warning and exit 0, so an `off/` tree would otherwise record runs that executed `all`.

**Tuning subsets** (#103): `bench/make_tuning_set.py <vanilla-results-tree> --instances bench/instances_plato.txt --size N --seed S` derives a stratified tuning list and prints the stratum table to stderr (the list goes to `--output`, stdout by default). It stratifies on **vanilla time-to-first-feasible** — read through `parse_highs_log`, not a second parser — because that is the axis the PLATO primal integral responds to; `bench/instances_small.txt` is stratified on *optimality* solve time and stays exactly as it is, being the recorded input of the retired budget-weight calibration and the set per-heuristic budget work runs on. Strata are half-open intervals split at `--boundaries` (default `1,10,100,600`) plus a `never` bucket and a `>=600s` overflow bucket — a solution found at or past the time limit is hard, not never-feasible, and must not be filed as one. Allocation is largest-remainder proportional in *integer* arithmetic, with `--min-per-stratum` seats reserved off the top so a 3-of-233 stratum is not rounded out of the set it was stratified for. The integer shares are load-bearing: with `room=[1, 1, 10]` and 4 seats to place the three remainders are a mathematical tie (4/12 each), but the float shares `0.3333333333333333, 0.3333333333333333, 3.3333333333333335` have fractional parts that sort 2, 0, 1, so a float implementation hands the seat to the third stratum where the stated rule (ties by stratum order) gives it to the first — an observed test failure, not a hypothetical. No cap is applied on top: `alloc <= population` follows from `rest <= room_total`, and a sweep in `bench/test_make_tuning_set.py` checks it rather than the code clamping something that cannot bind. The emitted header records source tree, config, seeds, boundaries, allocation rule and both distributions, and deliberately carries **no timestamp**: same tree plus same `--seed` must be byte-identical. It refuses (exit 2) any tree not covering the reference list for every seed of the config, and two log shapes that would otherwise be binned as never-feasible: a *truncated* log (no solving report), and one reporting a finite primal bound with no incumbent line — which is what a source code missing from `parse_highs_log._INCUMBENT_SOURCES` looks like, i.e. what a HiGHS bump produces. `parse_highs_log` already `warnings.warn`s on that second condition; `unusable_reason` mirrors it so the diagnosis becomes a refusal instead of a mis-binned instance in the smallest stratum, which `--min-per-stratum` then reserves a seat for. `--allow-incomplete-seeds` is the one documented escape, and it is recorded in the header.

**Instance filtering, the config oracle, and reference data** (#104): `--instances FILE` restricts any report to an instance list and `--exclude-instances FILE` removes one, applied in that order to the *raw* tree before aggregation — which is why every table reports the count it covers without knowing a filter ran, and why the held-out complement is `--instances plato --exclude-instances tuning` rather than a third file that drifts. `--oracle A B C` adds a best-of-those-configs row (`--oracle-name` renames it on collision, ≥2 participants required): selection is per instance on primal integral at `--time-limit`, **among exactly the seed-collapsed rows the tables already show**, which is what makes the row a true ceiling (headline SGM ≤ every participant's, instance by instance). Do not "fix" this into per-`(instance, seed)` selection followed by `aggregate_results`: that collapses picks chosen on primal integral by *median primal bound*, mixing two criteria, and the row can then score worse than a participant while still being labelled a ceiling — measured at ~2% of random two-seed trees. The oracle is additive and is held out of `#Win`/`#First` via the `synthetic` set. Instances absent from any participant at any shared seed, or outside the tables' common set, are dropped with the count reported — scoring an out-of-common instance is how the first version mis-selected, since `best_known` is built over that set and a missing reference sends `primal_integral` to the dual bound and the tie-break to whoever is named first. **"Virtual best" in that script is not the oracle** — it is `resolve_reference`'s handling of an observed primal that beats the published `.solu` value, and the module docstring says so; do not merge the two names. Reference objectives live in `bench/miplib2017-v36.solu`, a verbatim upstream copy (retrieved 2026-08-20) that replaced a stale `v22` marking `supportcase22` `=inf=`; an instance tagged `=inf=`/`=unbd=` is now excluded from every table with the exclusion printed, because the gap would otherwise fall back to the best observed primal and enter the SGM as a self-referential zero.

**`log_dev_level=3` used to be ruinous, and the patch now removes the reason.** Our instrumentation is `kVerbose`, which needs level 3, and HiGHS's own FeasibilityJump logged `Reached a local minimum.` at that same level from `updateWeights()` — once per weight bump, per parallel FJ worker, each with an `fflush`. That single line was **99.8% of a traced run's log volume and most of its cost**: on a 30 s presolve-only run of `50v-10` (2745 nonzeros, 16 workers) the log was 453 MB, and FJ charged 4.68e9 effort. `apply_patch.cmake` drops the line, and the same run is **8.7 MB and 1.01e11 effort — 52x less log for 21.6x more search, and `found` goes 0 → 1**. A clock-bound traced FJ dispatch was therefore not the same heuristic as an untraced one; that is fixed, not merely reduced (the earlier reading that level 3 costs "nil" for FJ was taken at effort 1.0, where FJ is *budget*-bound and finishes before the logging can cost it anything). What remains at level 3 is FJ's periodic table and our own two lines, so attribution and headline runs are much closer than the retired 1.1–4.4x — but they are still not the same run, and `run_benchmark.py` still leaves level 3 off behind `--dev-log`. One consequence to keep in mind: at level 3 a patched binary's FJ output no longer matches vanilla's — one of the reasons `off` is an ablation and not a vanilla proxy, and moot for `bench/check_vanilla_equivalence.py` since #147, which disables FJ on both sides and runs at the default log level anyway.

**Release archive** (#102): `bench/make_archive.py build <results-tree> --output <dir> --time-limit T` packages a results tree — logs, the `<instance>.opts` each run was given, generated tables, `MANIFEST.json` + `PROVENANCE.md` — and `verify` (wrapped by the archive's own `REGENERATE.sh`) re-derives every table from the archived logs and diffs it, so "regenerable from the archive alone" is checked rather than claimed. The provenance is *derived*, not asserted: which binary produced a config comes from the `mip-heuristics patch active` marker in each log, since patched and unpatched builds of the same tag have identical version/githash banners; the baseline's claim follows from that same marker, and there is exactly one baseline claim — "separately built unpatched binary". A baseline config whose logs carry the marker is recorded as "ablation on the patched binary — not a vanilla baseline" (#147 retired the old "vanilla-equivalent setting on the patched binary" wording, which offered a reader a weaker version of a claim that is not available at all); instrumentation is recorded both as requested (`log_dev_level` in the `.opts`) and as observed (`[Heur]`/`[Sequential]` tags), because a disagreement is the `--extra-options log_dev_level=1` failure. `--time-limit` is required because HiGHS takes it on the command line, so it is not in any `.opts`. The effective worker count is recorded the same derived way: the harness deliberately does not pin `threads`, so the count appears in no `.opts` and is read from each log's `Thread count N (of M threads)` line into `run.workers_observed` (`parse_highs_log` exposes the same three numbers as `thread_count` / `hardware_threads` / `max_workers` — `thread_count` is HiGHS's pool size and therefore `ExecutionContext::num_workers`, `max_workers` is B&B's own cap, and they are different numbers). Two distinct values across a tree means it mixes machines and its runs are not comparable, which warns; neither pinned nor observed warns too. The machine block itself is auto-detected on the *archive* host — hence `--machine-note`. A campaign yields two archives, headline-timing and `--dev-log` attribution; they are different runs. `docs/RELEASE.md` is the process around it, including the ordering constraint that Zenodo's GitHub integration must be enabled **before** the release is created (it does not backfill) and that `.zenodo.json` makes Zenodo ignore `CITATION.cff` entirely.
